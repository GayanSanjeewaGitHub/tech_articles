# The War Story

Four engineers split up a gnarly incident. Each takes a service, digs through logs, builds and runs things locally. Forty minutes later they reconvene — and three of them have been chasing the same wrong theory the whole time, because nobody said anything until the stand-up.

That's the bill here: a single AI coding agent handed a hard "understand this codebase" question resolves it a third of the time. Split the work across four agents with clean contexts and the accuracy barely moves, sometimes it gets *worse* on the hardest, most cross-cutting questions. You paid for four agents and bought yourself four narrower blind spots.

The reason is structural, not a smarts problem. Every multi-agent setup that exists lets agents talk only at phase boundaries — a handoff, a sync round, a shared file someone eventually reads. Mid-task, an agent that is working cannot also be listening. So the one teammate who stumbles onto the fact that rewrites everyone else's plan sits on it, silently, because surfacing it means stopping to write it down and hoping someone's watching.

**The fix isn't better division of labor — it's decoupling listening from working, so a discovery costs zero foreground steps to share.**

The mechanism is almost embarrassingly simple: a background watcher per agent, blocking on nothing.

```
while working_on_subtask():
    step()
    if discovery_matters_to_team():
        send_message(worklog, discovery)  # non-blocking, fire and forget
# separate background process, not a step:
watcher: on_mention -> surface_at_next_boundary()
```

No new model, no bigger context, no extra reasoning calls — just an OS process that lets a mention land between tool calls instead of at the next scheduled meeting. Task accuracy nearly doubled, and the gain grew fastest on exactly the hardest, most tangled tasks.

The question worth sitting with: how many of your own systems — human or agent — silently assume that coordination can wait until the next checkpoint?

# Section 2 — Practical Implementation

## What you'd need

- A coding-agent harness that can run an arbitrary shell command as a background/detached process (Claude Code, OpenCode, Codex CLI, or a custom ReAct-loop agent with subprocess support all qualify — no harness modification required).
- A tiny standalone message-broker process (the paper's "message server") that any agent can reach over a local socket, HTTP, or even a shared SQLite/Redis instance. It just needs to support three operations: create a named thread, append a message to a thread (optionally with @mentions), and let a caller block until a message mentions them.
- Multiple agent instances (the paper uses 4) pointed at the same repo/task, each with its own context window.
- A sandbox/container per task if you're doing anything destructive (build/run/test), matching how SWE-Atlas QnA is graded (agents may build and run code but not modify source files).
- No fine-tuning, no new model — this is pure orchestration/scaffolding.

## Minimal build, step by step

1. **Message server.** Stand up a small process exposing:
   - `create_thread(name, participants) -> thread_id`
   - `send_message(thread_id, content, mentions=[]) -> None` (returns immediately, no ack required)
   - `wait_for_mention(agent_id, timeout) -> (message, full_thread_snapshot)` (blocking call)
   A single-file Flask/FastAPI app backed by an in-memory dict or SQLite table is enough for a prototype; persistence only matters if you need to replay/debug runs.

2. **Agent-side shell scripts.** Wrap each primitive in a thin script (`create_thread.sh`, `send_message.sh`, `wait_for_mention.sh`) that the agent can invoke as tool calls. This is the only "integration" surface — the harness itself is untouched.

3. **The critical trick — background the watcher.** Instruct the agent (in its system/task prompt) to launch `wait_for_mention.sh` as a background job the moment it starts working (e.g., `nohup wait_for_mention.sh &` or the harness's native "run in background" tool), writing incoming messages to a local scratch file. The agent's foreground loop checks that scratch file at each step boundary and folds in anything new — it never spends a tool-call/step on listening. This is the entire "passive awareness" mechanism; everything else is workflow scaffolding around it.

4. **Five-phase protocol** (optional but is what made the numbers work in the paper):
   - **P1 Explore** — each agent independently explores the repo/task, drafts sub-questions, watcher already running.
   - **P2 Divide** — one agent (the assembler) opens a planning thread; agents negotiate a partition of sub-questions until everyone approves.
   - **P3 Execute** — each agent works its slice; on any discovery that bears on a teammate, contradicts the plan, or blocks an approach, it posts to a shared worklog thread immediately; incoming mentions get folded in at the agent's next step.
   - **P4 Review** — each agent posts findings + evidence to its own results thread; teammates flag conflicts or thin evidence, which can bounce work back to P3.
   - **P5 Submit** — assembler drafts the final answer, agents approve or request changes, assembler submits.

5. **Grading/acceptance criteria** — decide up front what "task resolved" means (the paper uses an LLM-judge scoring atomic rubric statements, pass only if all rubrics pass). For your own use case this could be unit tests passing, a human checklist, or a rubric-based LLM judge.

## Where it fits in a pipeline

This replaces the "fan out subagents, merge results" pattern (à la simple orchestrator/sub-agent designs) at the *execution* stage specifically — it's not a new planner and not a new agent-computer interface. It slots in as a communication layer sitting alongside whatever harness you already use; you keep your existing single-agent tool use, file-editing guardrails, and build/test tooling untouched. It's most useful for long-horizon, multi-file, multi-step *investigation* or *comprehension* tasks (root-cause analysis, architecture questions, security review, onboarding-style "how does this system work" questions) — not for tasks that are naturally sequential (the paper notes forced decomposition backfires on sequential tasks like Minecraft crafting plans, losing 39–70%).

## Gotchas / failure modes

- **Messages can derail an agent mid-evidence-gathering.** In the paper's rubric-level analysis, passive awareness gained 47 rubrics but lost 23 — a message arriving mid-execution sometimes pulls an agent off a line of reasoning that would have otherwise succeeded. Net positive, but not free; consider debouncing or prioritizing worklog posts.
- **It amplifies existing blind spots, it doesn't create new insight.** In the paper's Grafana case, no agent in either the blocking or passive condition ever concluded a required negative fact ("does not auto-select") — passive awareness gave a 0-point gain there because there was nothing correct to propagate. If no agent forms the right idea, broadcasting faster doesn't help.
- **Coordination overhead is real cost, not free lunch.** The full stack cost ~6x a single agent's API spend ($19.45 vs $2.96/task with Opus 4.6 in the paper). Compute-matched baselines (best-of-6 sampling) plateaued at 37.9%, far below the 62.1% from structured coordination — so the gain is from coordination, not raw compute, but you're still paying multiples.
- **Naive division alone can regress on cross-cutting questions.** Splitting work without negotiation actually lost tasks in the "architecture/system design" category (spanning many components) before recovering with a proper P2 negotiation phase. Don't skip the negotiate-the-partition step.
- **Watcher must be truly non-blocking/backgrounded** — if your harness can't detach a process (or you fake it with a foreground poll loop), you're back to the "blocking receive" baseline, which only gets you to L2 performance (51.6%), not L3 (62.1%). The entire gain is in that one architectural bit: where `wait_for_mention` executes.

## Toy walkthrough

Imagine 2 agents debugging why an API returns stale data.
- Agent A explores the caching layer, Agent B explores the DB layer. No negotiation (naive split): A assumes B will check TTLs, B assumes caching isn't in scope. Neither checks it — task fails.
- With negotiation (P2): they explicitly agree who owns "cache invalidation logic" before diverging.
- With passive awareness on top: mid-task, Agent B notices the DB write path never triggers a cache-bust event. Under blocking-only communication, B would have to stop and post-then-wait, or wait until the review phase to mention it — and might just forget, like the paper's MinIO case where an agent found `MINIO_AUDIT_WEBHOOK_ENABLE` was needed but never voiced it and the team unanimously signed off on the wrong answer. With a background watcher, B just fires `send_message(worklog, "no cache-bust on DB write, @A check invalidation code")` and keeps working; A's watcher picks it up at its next step and re-checks the invalidation path immediately — while there's still time to act, not after the postmortem is already drafted.

## When NOT to bother

- If a single agent already handles the task reasonably well (the paper notes: once single-agent accuracy exceeds roughly 45%, adding agents can yield *negative* returns) — don't add this complexity, it's solving a problem you don't have.
- If the task is genuinely sequential/non-decomposable (one step strictly depends on the prior step's output with no parallel sub-questions) — coordination overhead only adds cost and confusion; a single agent with a bigger context window or simple retry/self-critique loop is cheaper and works better.
- If you can't tolerate the ~6x API cost multiplier or can't stand up even a minimal message broker — a simpler "sequential handoff with a shared scratchpad file" gets you some of the division-of-labor benefit (L1/L2 level) without the infrastructure of a live messaging layer, just without the mid-execution correction gains.
