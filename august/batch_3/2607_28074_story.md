# SECTION 1 — The War Story

You spin up a fine-tuning run on a fresh batch of synthetic environments — a hundred fake apps, thousands of auto-generated tasks. The eval dashboard lights up green. Then you push the model at a live site and it faceplants: clicks a button twice, loops on a date picker, declares victory on a booking that never wrote to the database.

The pain isn't a crash — it's worse. It's a benchmark that keeps climbing while the model quietly gets *dumber* at the things that matter. You burned GPU-hours training on trajectories that looked correct and taught nothing, because the "app" underneath was a stage set: no permissions logic, no shared state, a guest-count field that silently ignores clicks. Every booking task built on it was already broken before the agent touched it.

Here's the mechanic nobody checks: a synthetic environment can pass every smoke test and still be shallow — visually convincing, structurally hollow. Train on it, and the model doesn't just fail to learn; it learns bad habits, because nothing ever pushed back on a wrong click.

**The fix is to stop treating environment count as the metric and start treating environment depth as gradable, then repair it on the same signal that grades the model.** Every rollout gets read twice — once as "did the agent succeed," once as "did the world hold together." A zero score triggers triage: is this the agent, or is this a broken control?

```
for rollout in graded_rollouts:
    verdict = verify_against_db(rollout)
    if verdict.fail:
        cause = triage(rollout)      # agent bug, or world defect?
        if cause == "world":
            repair(environment, tasks, verifier)   # fix first
        else:
            queue_for_training(rollout)            # trust the failure
```

One repaired guest-count control took a model's score on that world from 16% to 38%. Not because the model got smarter — because the thing grading it stopped lying.

So: when your eval number goes up, ask what would happen if you tried to break the thing scoring you.

# SECTION 2 — Practical Implementation

## What this paper actually is

**Echoverse** (Microsoft Research, arXiv:2607.28074) is a factory + training-loop system for building synthetic, stateful, database-backed applications ("worlds") to train computer-use agents, plus a **co-evolution loop** that uses every training rollout to both grade the model *and* repair the environment. Key numbers: a 9B model (Qwen3.5-9B) trained on 12 such worlds (21,009 verified trajectories) goes from 36.5% → 67.1% average task success across 14 eval splits, closing to within 14 points of the GPT-5.4 teacher that generated the data. Shallow environments actively *hurt* (80.0 → 75.0 on a live WebVoyager domain), while deep ones help (80.0 → 85.0, 48.0 → 65.0). RL on top of the SFT model (group-relative policy gradient, GRPO-style, over 5 worlds) lifts held-out judged score 58.8% → 68.0%.

## Core mechanism, precisely

1. **Environment = tuple (S, A, T, O, D0)** where state S is the app's *database*, not pixels. This is the load-bearing design choice — it makes reward groundable (diff the DB before/after) and reset exact (restore a per-task DB snapshot).
2. **Task = (goal, reference, kind)** where kind ∈ {READ, WRITE, READ_WRITE}. References are minted by running SQL against the live seed DB at generation time — the answer is true by construction, not by human labeling.
3. **Grading**: WRITE tasks are graded by `sqldiff(D0, D_final)` containing the required state change; READ tasks by semantic-equivalence LLM comparison of the agent's answer against a DB-sourced ground truth. The judge LLM (GPT-4.1 in their setup) never sees the trajectory or screenshots — only the final diff/answer vs. reference. This narrows the judge's job to "do these two facts match," which is why it's hard to game (as opposed to a screenshot-judging live-web benchmark).
4. **Depth checklist (Table 1)**: behavioural fidelity (controls/permissions/errors follow real logic), coherent cross-actor state (a sent message reaches its recipient), workflow depth (early choices constrain later steps), authoritative verification (DB not pixels), domain value.
5. **Factory pipeline (two phases)**: Phase 1 — seeds → spec → machine-checkable claims → generate app (FastAPI + SQLite + React) → verify claims against the running app via Playwright → repair (advance only when ≥95% of claims pass). Phase 2 — regenerate tasks grounded on the live DB → verify feasibility (white-box: an agent that reads source + queries DB checks if a goal is even reachable through the UI) → repair task/verifier/frontend/backend as needed → export when ≥95% of corpus passes.
6. **Co-evolution loop**: every failed rollout goes through the *same* verifier/triage agents that built the world. Coarse binary attribution: is this a model failure or a world/task/verifier defect? Defects get repaired (never by weakening the goal — that's treated as a regression); genuine model failures become training data. Triage groups failures by shared root cause so one fix (e.g., a broken date-picker control) can un-block dozens of tasks at once.
7. **RL stage**: GRPO-style group-relative advantage, NOT normalized by group std (per Liu et al. 2025 — avoids up-weighting near-unanimous groups). Reward = grounded trajectory reward (DB-diff judged) + dense per-step reward (multimodal judge, GPT-4.1 vision, binary per turn: did the action demonstrably change state?). Couplings prevent reward hacking: final-step dense reward forced to 0 if trajectory outcome is wrong; wrong termination penalized; dense term only applied to training rollouts (validation is pure grounded outcome).

## Step-by-step: building a minimal version yourself

You don't need Microsoft's scale to borrow the idea. A minimal version:

1. **Pick one real workflow** you want an agent to learn (e.g., "cancel a subscription," "file an expense report"). Don't clone the whole app — clone only the tables, routes, and screens that workflow actually touches (their "relative completeness" principle).
2. **Build a tiny backend + DB you own** (SQLite is enough) with real-ish seed data (hundreds of rows, not five placeholder rows — thin data is a top failure mode). Wrap a simple frontend around it (even a bare HTML form works for a v0).
3. **Write tasks as (goal, reference, kind) triples**, where the reference is generated by *querying the DB directly*, not hand-typed. E.g., "cancel Jane's Pro plan" → reference = `UPDATE subscriptions SET status='cancelled' WHERE user='jane'`.
4. **Build a grader that diffs the DB** before/after the agent runs, and checks whether the required diff is a subset of the actual diff (extra harmless changes are fine). For READ tasks, use an LLM call with a narrow prompt: "does this answer match this reference, allow rounding/paraphrase" (they publish their exact prompts in Appendix C — worth copying verbatim).
5. **Run a frontier model (e.g., GPT-4/5-class) against your tasks**, keep only the trajectories that pass the grader — this is your SFT corpus (rejection-sampled distillation, à la STaR).
6. **Close the loop**: when a task fails, don't assume the small model is bad — check whether the *task* is even completable (can you do it by hand through the UI?). If not, that's an environment bug — fix the environment/task/verifier, not the model.
7. **Fine-tune your target model** on the surviving trajectories. Optionally, once SFT plateaus, do a GRPO/PPO-style RL pass using the same grounded verifier as reward, with per-task pass-rate filtering (keep tasks the base policy solves 1-3 times out of 4 — discard the always-solved and never-solved ones, since both give zero-variance groups with no gradient).

## Where this fits in a pipeline

This replaces "scrape more web pages" or "buy more human-labeled demonstrations" as the data-generation stage for computer-use / GUI agents. It sits upstream of both SFT and RL: it's the environment + reward-model layer, not the policy architecture. It's a direct alternative/complement to live-web benchmarks (WebVoyager, Mind2Web) for *training* (they're fine for held-out *evaluation* since they can't be gamed by overfitting, but they can't reset state, throttle bots, and require screenshot-judging — useless as an RL reward source).

## Gotchas

- **Shallow-but-plausible environments are actively harmful**, not just useless — the paper shows a model trained on a shallow world scoring *below* the untrained baseline. If your synthetic app doesn't enforce real constraints (e.g., a form control that silently no-ops), you're teaching bad habits, not neutral ones.
- **Screenshot/vision judges as a training filter teach the policy the judge's blind spots** — and under RL this is worse, since the optimizer will find and exploit any judge weakness (reward hacking). Ground truth should come from actual state (DB), not "does this look right."
- **Trajectory volume saturates fast; environment diversity doesn't.** Their scaling experiment: 6,400 → 20,000 trajectories on the *same* worlds barely moved live-web transfer (54.8 → 55.6), while adding more distinct environments kept climbing. If you're stuck, generate more distinct tasks/environments before generating more rollouts of what you have.
- **A single missing UI affordance can silently invalidate an entire task class** (the guest-count bug). Test your environment by scripting agent-style interactions, not just manual QA — humans compensate for bad UI without noticing; agents don't.
- **Imitation has a hard ceiling**: a demonstration trajectory that never goes wrong teaches no recovery behavior and no "when to stop." If you only ever keep passing trajectories (rejection sampling), your model will never learn to recover from its own mistakes — that's what the RL stage is for.
- **95% is not 100%** — their own environments ship with a tolerated 5% claim-failure rate. Don't chase perfect environments; chase "good enough that failures are attributable."

## Toy walkthrough

Say you're training an agent to "book a table for 4 at 7pm." Your fake restaurant-reservation app has a party-size dropdown that the agent (which clicks via coordinates, not native `<select>` events) can't actually operate — it always leaves it at the default "2." Every reservation task with party_size ≠ 2 is *unwinnable*, no matter how good the model is. Naively, you'd log this as "model fails to set party size" and train harder on more failed rollouts — reinforcing confusion. Correctly, your triage step queries the DB after the run, sees party_size is stuck at 2 across all trajectories regardless of agent behavior, flags it as an *environment* defect, fixes the dropdown to respond to click+keyboard events, regenerates the task references from the fixed DB, and only *then* trusts subsequent failures as real agent capability gaps. This single fix might unblock dozens of tasks that all depended on that control — exactly the "one repair, many tasks cleared" effect the paper reports (48% → 78% completable bookings from one fix).

## When NOT to bother

- If your target domain is entirely on the **open, logged-out web** (read-mostly, no login, no persistent state) — live-web benchmarks like WebVoyager/Mind2Web are simpler and sufficient; you don't need to build a synthetic clone of Wikipedia.
- If you only need a **few dozen hand-checked examples** for a narrow eval, not a training corpus — hand-writing verifiers for a small fixed task set is far cheaper than standing up a whole synthetic application with an agent factory.
- If your task success is well-captured by a **simple text/output match** (e.g., "return this number," a stateless Q&A task) — you don't need database-grounded diffing; a simple exact/semantic-match check suffices, and building a stateful backend is overkill.
- If you don't have the ability to run **multi-agent build/verify/repair pipelines** (their factory uses GitHub Copilot SDK agents with terminal, Playwright, and DB-MCP access) — without that automation, hand-building even one "deep" environment is a significant software engineering project, and the ROI only shows up once you're training at real scale (thousands of trajectories, RL runs).
