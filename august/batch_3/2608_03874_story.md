## SECTION 1 — The War Story

You ship an agent with a "skills" folder. Give it a task, it writes a SKILL.md. Give it another, it writes another. A month in, someone asks: is this thing actually getting smarter, or just getting a bigger folder? Nobody can answer. The dashboard shows tasks passing. Nobody's watching the skill directory bloat past three hundred files nobody rereads.

That's the quiet failure. Not a crash — a plateau you can't even see, because "more skills accumulated" gets mistaken for "more capability gained." Teams ship the skill-library feature, declare victory, and never check whether skill #214 ever gets invoked again.

The hidden mechanic: a skill file is not the same thing as a lesson learned. An agent chasing this task's rubric will happily write a skill that memorizes this task — a slightly-generalized dumping ground of what just worked. It compiles, it loads, it looks like consolidation. But nothing forces abstraction. Fragmentation feels identical to learning from the inside.

**The shift: stop asking "did it save a skill file," start asking "did it reuse one it didn't just write."**

The fix isn't a smarter prompt — it's a scoreboard. Run every task twice: once with full memory and skill-writing rights, once cold, from scratch, no memory. The gap between them is your real signal. Then split that gap again: run a third arm with memory and feedback but *no skill files allowed* — pure in-context carryover. If that arm matches the skill-maintaining one, your skill library isn't the thing doing the work. Context is.

```
gap_total   = reward(sequential+skills) - reward(cold)
gap_skills  = reward(sequential+skills) - reward(sequential+context_only)
```

One benchmark ran this on real agents across five domains. The skill library added almost nothing on average — 0.602 vs 0.605 for context alone. But weaker models kept writing more files anyway, each one thinner, less reused, lower quality.

So: when your agent "learns," ask what's actually carrying the improvement — the file it wrote, or just the conversation it's still in.

## SECTION 2 — Practical Implementation

### What the paper actually is

The paper introduces **ContinualSkillBench**: five domains (Law, Healthcare, Finance, Math, Office), 100 tasks each, ordered by difficulty and by a skill-dependency graph so later tasks can plausibly reuse skills from earlier ones. Agents run through the 100-task stream with a **three-turn protocol per subtask**: (1) task + current skill index, (2) execute, (3) read judge feedback and optionally call `create-skill` / `modify-skill` meta-skills to update a persistent skill repository (Markdown files with YAML front matter, similar to Claude Code / Codex CLI skill files). They compare:

- **Independent**: memoryless, zero-shot on each task, skill repo reset every time (control).
- **Sequential**: full memory + persistent, growing skill library.
- **ICL (in-context learning) baseline**: same memory/feedback as Sequential, but *cannot* write or edit skill files — isolates "adaptation from context" from "explicit skill abstraction."
- **RAG baseline**: instead of skill files, indexes and retrieves prior trajectory snippets.

Headline numbers: sequential execution beats independent in 14/15 model-domain pairs (+16.9% relative normalized reward on average), but the *explicit skill repository specifically* is nearly a wash against pure ICL (0.605 ICL vs 0.602 Sequential, averaged over Law/Finance/Healthcare on GPT-5.3-Codex). Weaker models (GPT-4o) accumulate huge, fragmented skill pools (384 skills, avg quality 5.68/10 by an LLM judge) that get reused rarely; stronger models (GPT-5.3-Codex) keep a compact pool (205 skills, avg quality 7.94) that gets invoked far more often.

### What you'd need to try this yourself

- An agent harness that already supports persistent state across a task loop (Claude Code, Codex CLI, or a custom loop around any tool-using LLM) — something with a place to read/write files between turns.
- A **stream of related tasks**, not one-off benchmarks — ideally with a natural difficulty/dependency order (or you can order them yourself by tagging required sub-skills).
- A **judge/evaluator per task** (exact match, numeric tolerance, an LLM rubric judge, or programmatic checks against output files) — you need per-task reward to know if anything is improving.
- Optionally: a sentence-embedding model (paper uses `all-mpnet-base-v2`) if you want to measure skill-reuse structurally rather than just anecdotally.
- Compute budget: this is expensive because you must run *the same task sequence at least twice* (Independent and Sequential) to compute a delta, and ideally three times if you want to isolate explicit-skill value with an ICL arm.

### Minimal implementation sketch

```python
def run_stream(tasks, mode):  # mode in {"independent", "icl", "sequential"}
    skills = {} if mode != "independent" else None
    memory = [] if mode != "independent" else None
    rewards = []
    for task in tasks:
        if mode == "independent":
            skills, memory = {}, []  # hard reset every task
        context = build_prompt(task, skills, memory)
        output = agent.run(context)
        reward, feedback = judge(task, output)
        rewards.append(reward)
        if mode != "independent":
            memory.append((task, output, feedback))
        if mode == "sequential":
            # reflection turn: let the agent create/modify a skill file
            update = agent.run(reflect_prompt(feedback, skills))
            skills = apply_skill_update(skills, update)
    return rewards

ind_rewards = run_stream(tasks, "independent")
icl_rewards = run_stream(tasks, "icl")
seq_rewards = run_stream(tasks, "sequential")

gap_total  = mean(seq_rewards) - mean(ind_rewards)
gap_skills = mean(seq_rewards) - mean(icl_rewards)   # the number that actually matters
```

Steps in plain English:
1. Pick a domain where you already have ~50-100 real tasks with some kind of gradable answer (support tickets with resolutions, code review comments with a merge/no-merge outcome, financial Q&A with numeric answers — anything you can score).
2. Order them, even crudely, from easy to hard, and tag each with 1-3 "skills" it probably exercises (an LLM can do this tagging for you, as the paper does with GPT-5.4).
3. Build the three-turn loop: instruction → execution → reflection-with-optional-skill-write.
4. Give the reflection turn a strict template forcing abstraction: "don't restate this task's specifics; write the general rule, the trigger condition for using it, and one failure mode." This is the part that most implementations skip and where quality collapses — see the GPT-4o skill examples in the paper (`date-range-filter`, hardcoded to one trading task) vs GPT-5.3-Codex's (`tatqa-metric-alignment`, a genuine decision procedure with priority rules and pitfalls).
5. Track skill **call frequency**, not just skill count. A skill nobody re-invokes is dead weight, and a growing-but-unused pool is the fragmentation failure mode the paper documents (Figure 3: GPT-4o writes 4x more skills than GPT-5.3-Codex but gets called on a smaller fraction of them).
6. Run all three arms (independent, ICL, sequential) on the same task order and compare `gap_total` vs `gap_skills`.

### Where this fits in a real pipeline

This replaces "static prompt + fixed tool list" agent deployments with a self-updating one, and it plugs in wherever an agent handles a recurring task type over time (a coding agent's project-specific conventions, a support-triage agent's escalation rules, a data-analysis agent's per-client quirks). It sits *between* your evaluation harness and your agent's system prompt/tool config — the skill files effectively become a dynamically-grown appendix to the system prompt, loaded selectively per task.

It is explicitly not a replacement for fine-tuning or RAG over a real knowledge base — it's a lightweight, no-training way to accumulate *procedural* knowledge ("how to do X here") rather than *factual* knowledge ("what is X").

### Gotchas

- **Skill write ≠ skill value.** Don't count skills created as a success metric. Track reuse rate and, ideally, run a periodic LLM-judge quality pass (the paper's rubric: front-matter validity, specificity, procedure steps, generalization, anti-pitfalls, verification, minimality, toolability) — a skill with great content but broken YAML front matter is worth zero because it silently fails to load.
- **Reflection prompts must actively forbid memorization.** Left unconstrained, agents write skills that are thinly-veiled task-specific hacks (hardcoded paths, task IDs, one-off constants). This is the single biggest lever on skill quality, and it costs nothing but prompt engineering.
- **Unbounded growth degrades the system.** A skill index that's grown to hundreds of files makes turn 1 ("review available skills") itself an expensive, imperfect retrieval problem — you need pruning/merging, not just accretion. The paper doesn't solve this; it's flagged as the open failure mode.
- **The independent-vs-sequential comparison alone will fool you.** It conflates three different effects (retained context, feedback adaptation, explicit skills). If you only run two arms you'll likely overcredit your skill-writing feature — always add the ICL-only arm before claiming the skill library is what's driving gains.
- **Evaluator type matters.** Structured/exact-match/numeric tasks show the clearest gains from explicit skills (stabilizing output format, precise procedures); open-ended rubric-judged tasks often benefit *more* from plain context adaptation and can even regress with skills that over-fit to earlier rubric criteria (Opus 4.7 dropped -0.192 on Math rubric scores in one run).

### Toy walkthrough

Imagine a support-bot answering "what's our refund policy for X" across 100 tickets in increasing complexity. Ticket 3 teaches it "refunds require order ID + purchase date within 30 days" — written as a skill. Ticket 47 is "customer wants refund on a subscription, not a one-time purchase." If the ticket-3 skill was written narrowly ("one-time purchase refund needs order ID"), it doesn't fire for ticket 47, and the bot re-derives everything from scratch (fragmentation). If it was written well ("refund eligibility check: (a) identify purchase type, (b) apply type-specific window, (c) verify ID"), ticket 47 hits the trigger, reuses step (a)/(c), and only needs new logic for the subscription window (consolidation). The paper's finding is that most agents, most of the time, land closer to the first case than the second — and that plain conversation memory (ICL) does almost as much lifting as the skill file did.

### When not to bother

If your task volume is low, your tasks are largely independent (little real skill overlap), or a single well-written static system prompt / few-shot example set already covers your cases, skip this — the three-arm evaluation overhead and skill-quality tooling aren't worth it. Simple RAG over a curated knowledge base, or just a good static skills folder maintained by a human, will usually match or beat what an agent self-evolves, at a fraction of the engineering and API cost. Only invest in self-evolving skills when tasks genuinely recur with variation over a long-running session and you can't afford to hand-author the procedures ahead of time.
