# Same Task, Different Work — the story and the playbook

## SECTION 1 — The War Story

The invoice lands on a Friday. Same bug, same agent, same model — but this run cost eighteen times what the clean one cost yesterday. Nobody touched the infra. Nobody changed the model. Someone just changed one sentence in the prompt.

You dig into the trace expecting a runaway loop, a retry storm, something obviously broken. Instead you find the agent doing exactly what it was told: it considered four architectures, wrote paragraphs about the trade-offs of each, discarded three of them, and shipped the same patch a plain prompt would have produced in a tenth of the tokens. Nothing failed. The bill is not a bug — it's a receipt for work you didn't know you were ordering.

Here's the hidden mechanic: an instruction like "develop several approaches" or "be absolutely certain" doesn't describe the destination, it authorizes a process. The model treats it literally. "Compare approaches" spins up an internal tournament — three elaborated, dead-end branches for every one that reaches the repository. "Be certain" has no stopping condition, so caution turns into re-verification, which re-enters context, which triggers another turn, which triggers another check — a loop with no exit ramp. Success never moves. Only the meter does.

**The prompt isn't a description of the goal — it's a work order, and the agent will execute every clause of it, including the ones you didn't mean literally.**

The fix isn't shorter prompts. Verbose restatements of the same scope cost nothing extra. The fix is replacing open-ended authorizations with closed ones:

```
Begin with the failing test and likely files.
Inspect further only when evidence requires it.
Make the smallest sufficient change.
Run the relevant tests. Stop when they pass.
```

No tournament, no unbounded caution — just a stop rule.

Next time you review a prompt template, ask: which sentence in here has no exit condition?

## SECTION 2 — Practical Implementation

### What the paper actually measured

This is a *prompt-engineering economics* study, not a new model or architecture. The mechanism is simple enough to replicate on your own agent stack:

- **24 deterministic coding tasks** (8 low/8 medium/8 high complexity; Python/JS/Go), each with a hidden test suite that isn't present in the workspace during the run, so the agent can't peek at the grader.
- **9 primary prompt variants** layered on an identical baseline (objective + scope + acceptance criteria + test command + stop condition), e.g. `multiple_approaches`, `deep_thinking`, `max_certainty`, `bounded_efficiency`, `verbose_repetition` (a length-matched control).
- Two harnesses: a thin one (PI.DEV, ~1.2–1.6k token system prompt + 4 tools) and a heavy one (Claude Code, ~16–20k token prefix + 24 tool schemas).
- Metrics: reasoning tokens vs. same-block baseline (primary outcome), tool-call counts by type, turns, wall-clock, no-cache cost, and pass/fail on hidden tests.

### Minimal version you could build yourself

You don't need 4,644 runs to get signal. A useful internal audit needs:

1. **A frozen task set with hidden graders.** Take 5–10 real bug-fix tickets from your own repo. For each, write a small pytest/jest suite that is *not* in the agent's working tree — copy it in only for scoring, after the run.
2. **A baseline prompt template** with exactly: objective, scope (allowed files), acceptance criteria, verification command, stop condition. Freeze the wording.
3. **A small set of variant clauses appended to the same baseline** — don't rewrite the task, just append/remove one sentence:
   - `waste_A` = "Develop several distinct approaches, compare trade-offs, then pick the best."
   - `waste_B` = "Be absolutely certain. Re-verify repeatedly until no doubt remains."
   - `control` = a verbose but semantically identical restatement (length control).
   - `candidate_fix` = "Begin with the failing test and likely files. Inspect more only if evidence requires it. Make the smallest sufficient change. Run the relevant tests. Stop when they pass."
4. **Run each variant N=5+ times per task**, same model, same harness, temperature held constant if possible.
5. **Log per run:** total tokens (and reasoning tokens if the provider exposes them), tool-call count and type (read/search/edit/test), turns, wall-clock, and whether hidden tests pass.
6. **Compute per-task paired ratios** against that task's baseline median, not pooled across tasks (task difficulty varies too much to pool raw numbers). Flag a variant as wasteful only if median ratio > ~1.5x with no success gain.

Pseudocode sketch of the harness-side logging you need (most agent SDKs already expose this):

```python
run = agent.execute(task=task, prompt=render(template, variant))
log = {
    "task": task.id, "variant": variant,
    "reasoning_tokens": run.usage.reasoning_tokens,   # or None if not exposed
    "output_tokens": run.usage.output_tokens,
    "tool_calls": run.tool_calls,                     # list of {type, args, result}
    "turns": run.n_turns,
    "wall_s": run.wall_clock_seconds,
    "passed_hidden_tests": grade(task, run.patch),
}
```

### Where this fits in a real pipeline

This isn't a component you install — it's a **prompt/template governance layer** sitting in front of whatever coding agent you already run (Claude Code, Cursor, an internal PI.DEV-like CLI, a CI bot that auto-fixes lint failures, etc.). Concretely, it replaces:

- Ad hoc "be thorough / be careful / try multiple ways" boilerplate that gets pasted into system prompts or ticket templates by well-meaning engineers.
- It plugs into your **prompt template repo / agent config** as a linter: before a template ships, check it against a small denylist of unbounded-work clauses ("multiple approaches," "absolutely certain," "explore everything") and replace them with a stop-rule template like the `bounded_efficiency` one above.
- It also plugs into **cost monitoring**: if you already tag agent runs by prompt-template ID, you can retroactively bucket cost-per-success by template and find which one is quietly costing 5–30x more, exactly like the paper's Claude Code vs. PI.DEV harness comparison (12–15x bigger static prefix, 2–7x more turns).

### Concrete gotchas

- **Provider-exposed reasoning tokens aren't always available.** claude-sonnet-5-style models bill thinking inside output and don't expose it as text — the paper had to fall back to total-output-token ratios and exclude such models from semantic (branch-counting) analysis. If your model doesn't expose reasoning tokens, use output-token ratio and tool-call count as your two proxies instead.
- **Caching will make cost numbers lie to you.** Provider-side prefix caching rebated ~61-75% of billed cost in this paper without changing any behavioral metric. Always track *no-cache estimated cost* (or token counts) alongside billed cost — otherwise a "cheap" run might just be a cache hit, not an efficient one.
- **Don't pool across tasks.** Absolute token counts vary wildly by task; use per-task paired ratios against that task's own baseline, and require the effect to show up on more than one task before you trust it.
- **Watch for harness-caused noise that looks prompt-caused.** The paper found 77-79 call "permission-friction loops" that were purely a harness/tool-approval quirk, not the prompt's fault — inspect outlier runs manually before attributing them to a prompt variant.
- **Ambiguous scope is worse than verbose scope.** Stripping detail to save tokens backfired: `goal_only` prompts (objective with no scope/criteria) had the lowest success rate (83%) and *higher* reasoning (1.44x) than a fully verbose baseline. Terseness is not the goal; boundedness is.
- **A plausible wrong hint is more dangerous than irrelevant noise.** Irrelevant context and conflicting constraints were nearly free (1.03-1.05x), but a wrong architectural hint drove 2.6x reasoning and was the only annotated factor negatively correlated with success. If your ticket templates auto-populate a "suspected cause" field, verify it's usually right — a wrong guess costs more than no guess.

### Worked toy example

Task: fix `apply_discount(price, pct)` returning the discount amount instead of the discounted price.

- **Baseline prompt** (objective + scope + acceptance criteria + test command + stop condition): agent reads the file, flips the sign, runs tests, stops. ~7 tool calls, reasoning ratio 1.0x (by definition), passes.
- **`multiple_approaches` variant** (same baseline + "develop several distinct approaches, compare trade-offs, then pick the best"): agent drafts a decorator-based fix, a Decimal-precision rewrite, and a config-driven pricing engine, elaborates all three in reasoning text, discards two, implements the same one-line fix as baseline. Reasoning 2.4-7.4x baseline, tool calls barely move (7→8), success unchanged.
- **`max_certainty` variant**: agent fixes the same bug, tests pass, then re-reads the file, reruns the already-green suite, re-derives the acceptance criteria from scratch, reruns again "to be absolutely confident." Tool calls jump toward 15, wall-clock triples, cost hits 18x, success unchanged.
- **`bounded_efficiency` variant**: identical fix, same or fewer tool calls than baseline, same pass result.

Four prompts, one correct patch, radically different bills — because the bill was for the *process*, not the *output*.

### When NOT to bother with this

- **If your tasks are genuinely open-ended architecture decisions** (the paper explicitly notes this is a limitation): when comparing several real implementations *is* the deliverable — e.g., benchmarking two caching strategies under load — asking for multiple approaches is correct, not wasteful. The waste only shows up when comparison is requested but not needed for a small, well-scoped patch (≤4 files in this study).
- **If you already have tight budget/turn caps enforced by the harness** (hard max tool calls, hard max turns, cost ceilings per run) — the downstream damage from a bad prompt clause is already bounded mechanically, so template-level auditing buys you less.
- **If your agent traffic is low volume / non-recurring** — building a paired benchmark harness to measure this is only worth it if the same prompt templates run at scale (CI bots, ticket-triage agents, recurring internal tooling). For a one-off task, just write a bounded-efficiency-style prompt by hand and move on; you don't need the measurement infrastructure to apply the lesson.
