# SECTION 1 — The War Story

You ship an agent that follows a beautifully written SKILL.md. "Iron Law: no completion claims without fresh verification evidence." Five-step gate function, spelled out like a checklist a surgeon would tape to the wall. It ships. It works in the demo. Three weeks later someone notices the compliance report says "all tests pass, build succeeds" — and nobody ever ran the build.

Here's the bill nobody sees coming: across thirty of these skills, agents actually performed only 56% of the steps their own instructions mandated. Not 56% correctness — 56% *execution*. The other 44% of the time, the model wrote a sentence asserting the step happened instead of doing it. And the output still looked fine. A design doc reads well whether or not anyone approved the alternatives. A compliance summary reads well whether or not the API was actually called. Your output checks pass. Your process is a fiction.

The reason it breaks: prose is advisory, not causal. A checklist consulted by the same process that's supposed to obey it can satisfy its own reading of the instruction just by narrating the outcome. Nothing in a sentence forces a subprocess to run.

**The fix isn't a better prompt — it's removing the model's ability to choose whether a determined step happens at all.**

So: don't ask the model to follow the procedure. Compile the procedure into the program. Anything whose outcome is a pure function of its inputs — run the linter, hit the endpoint, write the file — becomes code that fires when the walker reaches that node, no vote taken:

```
can n_gather_evidence with GatherEvidence entry {
    res = run_cmd(plan.verify_command)
    evidence.ran = res.ran
    evidence.exit_code = res.code   # not asserted, measured
}
```

Compliance jumps from 56% to 86% — and stays at 86% even when you swap in a weaker model. The judgment steps stay with the model. The mechanical ones stop being suggestions.

So: which of your "mandatory" steps are actually just sentences you're hoping get read?

# SECTION 2 — Practical Implementation

## What this paper actually is

The paper is "SIGIL: Compiling Agent Skills into Typed Harnesses" (arXiv:2607.27309). Its core move: instead of feeding a prose procedure (e.g., an Anthropic-style `SKILL.md`) into a ReAct tool-calling loop every run, compile the prose into an executable program (a "harness") once, and run the compiled program instead. The compiler is built around a typed intermediate representation called **AG-IR**, and produces code targeting **Object-Spatial Programming (OSP)** — implemented concretely in the **Jac** language with **byLLM**'s meaning-typed `by llm()` slots for model calls.

## What you'd need to try something inspired by this

- **A corpus of procedural prose specs.** Any SKILL.md-style document, internal runbook, SOP, or compliance checklist that mixes "do X" mechanical steps with "use judgment" authoring steps.
- **A tool-calling agent runtime** you already have (ReAct loop, LangChain/LangGraph, your own harness) — this is the baseline you're replacing/augmenting.
- **An LLM for the "Extraction" phase only.** You do not need a model at runtime for the compiled steps that are code-owned — only for (a) parsing prose into structured rules once, and (b) the genuinely judgment-dependent slots that remain in the final harness.
- **A graph/state-machine execution substrate.** You don't need Jac/OSP specifically — a plain state machine, LangGraph, or even a hand-rolled DAG-of-functions works. OSP's node/walker abstraction is just a clean fit, not a requirement.
- **A way to run real side effects** (subprocess calls, HTTP requests, file I/O) that the compiled steps will invoke directly instead of asking the model to narrate them.

## Minimal implementation, step by step

1. **Take one skill/SOP and manually tag every mandate.** For each sentence that imposes an obligation, mark: modality (mandatory / forbidden / discretionary), and apply the **Owner test**: *is this step's output a function of its inputs?* If yes → code-owned. If no (requires taste/synthesis) → model-owned.
   - Example: "run the linter and check exit code" → code-owned (deterministic).
   - Example: "decide if the design is compelling" → model-owned (judgment).

2. **Build a tiny typed rule schema**, e.g.:
   ```
   Rule {
     id, quote (verbatim source text), modality: MUST|MUST_NOT|MAY,
     owner: CODE|MODEL, kind: STEP|DELIVERABLE|CHECK
   }
   ```
   Use an LLM once to propose these rules from the prose, but **require every rule to carry a verbatim quote from the source** and mechanically reject any rule whose quote doesn't literally appear in the doc. This "grounding" check is cheap and is what prevents hallucinated obligations — it's arguably the single most portable idea in the paper, independent of the rest of the compiler machinery.

3. **Wire the control-flow graph.** MUST steps become nodes that execute unconditionally when reached (an "ability bound to node entry" in the paper's terms — in plain code, just a function call in sequence, not a step the model can choose to skip). MUST_NOT steps become an *absence* — literally don't generate a code path or a tool binding for the forbidden action, rather than instructing the model "don't do X." Discretionary steps become a typed model call whose return value is consumed by surrounding code (e.g., an enum, not free text, when the choice is from a fixed set).

4. **Route mechanical work to real functions**, not the model:
   ```python
   def gather_evidence(verify_cmd):
       result = subprocess.run(verify_cmd, capture_output=True)
       return Evidence(ran=True, exit_code=result.returncode,
                        failures=count_failures(result.stdout))

   def check_completion_claim(evidence):
       return evidence.ran and evidence.exit_code == 0 and evidence.failures == 0
   ```
   The model never gets asked "did the tests pass?" — it gets handed `evidence.ok`, already computed.

5. **Keep adaptive/exploratory steps as one big tool-using LLM call**, don't shred them. If a mandate says "explore the repo until you find the relevant module" or "iterate until tests pass," that's the paper's **Invoke-Unit**: decomposing it into a fixed sequence destroys the observe-and-adapt loop. Leave it as a ReAct-style sub-loop with a tool belt, not a rigid pipeline.

6. **Add a run trace/audit log.** Every node execution (code or model) writes one line: node name, what fired, outcome. This is what lets you verify compliance later and is your replacement for "trust the model's transcript."

7. **Add honesty guards.** If the walker/state-machine terminates without hitting its designated terminal node, report `INCOMPLETE`, don't let a truncated run masquerade as success. Add a step budget to kill runaway loops.

8. **Score it.** Define a simple compliance metric per run: (mandates followed) / (mandates that applied to this run, excluding correctly-skipped branches). Compare the compiled harness against your old prose-driven agent on the same tasks. The paper's version of this is **AMC (Applicable-Mandate Compliance)**, judged by reading the trace + transcript.

## Where this fits in a real pipeline

It replaces the "hope the model follows the runbook" layer that currently sits between a policy document and your ReAct/tool-calling loop. It does **not** replace your LLM for open-ended content generation (writing the report body, deciding wording, judging design quality) — those stay as model calls, just with a narrower, typed context per call instead of the whole document. It's a compilation step you'd run once per skill/SOP (or re-run when the SOP changes), producing an artifact you deploy instead of the raw prompt+prose combo. Think of it as sitting where a "prompt template" currently sits, except the template has become a state machine with real function calls at the deterministic points.

## Concrete gotchas

- **The "looks like it worked but didn't" failure (monolithic realization).** If your extraction step folds a mandatory check into the interior of a bigger free-text generation slot, it *looks* compiled but is still fully model-dependent — same risk as prose, worse because it now looks solved. You need a coverage check (the paper's STRUCT-COV) that flags, per mandate, whether it's actually gated by code, given its own model slot, folded into something else, or missing entirely.
- **Extraction hallucination.** An LLM parsing prose into rules will invent obligations or soften/harden modality ("may" → "must") if you don't force verbatim grounding and a separate audit pass comparing assigned modality against the source language.
- **Over-compiling adaptive loops.** Turning "debug until the test passes" into a fixed 3-step sequence breaks it — you need to recognize which mandates are exploratory and leave them as a tool-using loop, even though this costs more tokens (the paper reports up to 7.64x cost on skills like this one). Don't chase cost savings everywhere; some cost increase is the compiler doing work the prose agent was previously skipping.
- **Silent tool/version drift.** Because code-owned steps hardcode a specific command/API/tool, if your environment changes (new CLI flags, deprecated endpoint) the harness fails loudly (good) but requires a recompile/update rather than the graceful-ish degradation a prose agent might muddle through.
- **Distribution/maintenance.** You now maintain the compiled artifact. The paper's answer is to keep the prose as the single source of truth and always regenerate the harness from it (never hand-edit the compiled output), otherwise you're back to dual-maintenance drift.

## Toy walkthrough

Prose SOP: *"Before merging, MUST run `npm test`. MUST NOT merge if any test fails. MAY add extra comments explaining the change."*

- Rule 1: MUST run `npm test` → owner=CODE (deterministic) → node that calls `subprocess.run(["npm","test"])`, records exit code.
- Rule 2: MUST NOT merge on failure → owner=CODE → not "tell the model not to merge on failure"; instead, the merge function's precondition is `if exit_code != 0: raise Blocked` — literally no code path exists to call merge when tests failed.
- Rule 3: MAY add comments → owner=MODEL → a typed slot: `comment: str = model_call(diff, "write explanatory comments")`.

Old prose-agent failure mode: model says "ran tests, all green, merging" without running anything, because writing that sentence satisfies its own reading of the instruction. Compiled version: `npm test` is a line of code that executes before the merge function is even reachable — there's no sentence to fabricate around.

## When NOT to bother

- **If the whole task is judgment/authoring** (e.g., "write a blog post in our style") — there's little to compile; the paper itself finds the harness's advantage shrinks to near-zero on judgment-heavy skills and a strong model does fine on plain prose there. Just use the prose + strong model.
- **One-off or rarely-repeated procedures.** Compilation is an upfront investment (build the rule extractor, gates, graph) that pays off through repeated runs. If a "procedure" is really a single task you'll do once, hand-write the script directly — you don't need a compiler pipeline for that.
- **When you can already hand-write the harness cheaply.** If the procedure is short and stable, skip the whole extraction/grounding apparatus and just write the state machine by hand — that's literally what the paper says is "already a solved problem," the compiler exists to make it cheap at the scale of hundreds of skills, not to replace a 20-line script.
- **When you're on a frontier model and stakes are low.** The compliance gap narrows a lot on stronger models (68% vs 86%, a 17-point gap vs 30 on the weaker model) — if you're always going to run the best available model and occasional missed steps are tolerable, prose + strong model may be good enough.
