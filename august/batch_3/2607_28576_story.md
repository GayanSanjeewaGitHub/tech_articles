# The War Story

Someone on your team ships a "smarter" pipeline: the model critiques its own answer, rewrites it, checks itself, repeats. The eval dashboard goes green. Champagne emojis in Slack. Nobody looks at the bill.

The bill is the pain. That critique-and-rewrite loop is seven model calls where a plain answer took one. Of course it scores higher — you gave it seven times the compute. The dashboard can't tell you whether the *idea* helped or whether you just paid more. It's the same trick as declaring victory because you retrained on 7x the data and forgot to mention it.

The hidden mechanic: nearly every "reasoning" technique — plan first, critique, reflect, debate — is secretly a budget increase wearing a methodology costume. And budget increases help almost regardless of shape. So the entire literature has been comparing a funded team against an unfunded one and calling it a fair fight.

**The shift: stop asking "did the method help" and start asking "did it beat spending those same tokens on something dumber."**

The fix: hold the token budget fixed. Take the exact compute a critique-loop would burn and instead spend it on independent attempts, then vote:

```
samples = [ask_model(q) for _ in range(N)]
answer  = most_common(extract_answer(s) for s in samples)
```

Across model sizes and math benchmarks, nothing beats this at equal cost. Ten methods lose outright — every one of them a method where the model inspects its own output. The killer isolation: give Best-of-N and majority-vote the *identical* eight samples. Same tokens, same model. Only the last step differs — model picks vs. tally counts. Counting wins by up to 17 points. The model is good enough to produce the right answer; it isn't good enough to recognize it.

Worse: one self-checking method never even fired its retry — it just rubber-stamped itself "correct" every time, quietly becoming a single answer while still billed as the fancy version.

If your evals reward a technique, ask what it actually bought — more thinking, or just more tokens.

# Practical Implementation

**What you'd need**
- Any instruction-tuned open model you can sample from at temperature > 0 (the paper uses Qwen2.5 1.5B/3B/7B via llama.cpp on CPU — no GPU required, just patience: ~30-60 tok/s single-stream).
- A benchmark or task with a checkable, comparable answer (math with a final numeric/formula answer is ideal — GSM8K, MATH-500). Majority voting *requires* answers that can be tested for equality; it doesn't work on open-ended prose.
- Ability to log per-call token usage (`usage.completion_tokens` from an OpenAI-compatible server, or your own tokenizer) — this is the whole ballgame, so don't skip it.
- A deterministic answer extractor (last `\boxed{...}` with real brace matching, or "the answer is", or last number) and a grader with tolerance for numeric compare / LaTeX normalization for symbolic compare.

**Step-by-step minimal version**
1. Pick a fixed set of ~150+ questions (100 is too few — standard error on paired differences runs 1.3–3.2pp at n=150; at n=100 your CI is ±3–8pp, useless for detecting anything under 5-6pp).
2. For each question, generate a pool of K=16 independent samples at temp 0.7. Store every raw generation and its token count.
3. Build the self-consistency curve for free from this one pool: for each N in {1,2,3,4,6,8,12,16}, repeatedly draw N samples without replacement (~200 draws), take majority vote, average accuracy and cost. This gives you a full accuracy-vs-cost curve from one pool instead of rerunning generation at every N.
4. Implement your candidate method (Self-Refine, Reflexion, Best-of-N+verify, debate, whatever) exactly as described, logging every token from every call — critiques, reflections, verification prompts, debate turns, all of it count as cost.
5. Compute the method's mean total token cost c. Interpolate the self-consistency curve (linearly, in cost-accuracy space) to find its accuracy at that same cost c.
6. Compare method accuracy vs. interpolated baseline accuracy with a **paired bootstrap** over questions (10,000 resamples, same question set for both arms), report a 95% CI. If testing multiple methods at once, apply Holm-Bonferroni correction.
7. To isolate "is it the tokens or the self-judgment," run the Best-of-N ablation: take the same N samples, score them once via the method's own selection step (model picks) and once via plain majority vote. Same samples, same tokens — only the aggregation rule changes.

**Where this fits in a pipeline**
This is an evaluation harness, not a production component — it replaces "run method X, report accuracy" with "run method X, run self-consistency at the same price, compare." Bolt it onto any inference-scaling or agentic-reasoning pipeline before you ship a technique that spends more tokens per query. It's a gate: before a self-critique/reflection/debate feature graduates from prototype, run it through this budget-matched check against plain repeated sampling.

**Gotchas**
- Deterministic (temp-0) methods vs. temp>0 baseline confounds temperature with method — control for it by also comparing greedy CoT against SC@1 (a single temp-0.7 sample), which costs about the same and isolates the temperature effect.
- Self-triggered control flow (e.g., "reflect only if you judge yourself wrong") can silently collapse into a cheaper method — a model that always says "I'm correct" never reflects, and you'll score a fancy method that's secretly one chain of thought. Always log and report how often the adaptive branch actually fires.
- Long-context verification prompts (e.g., stuffing 8 full candidate solutions into one prompt for Best-of-N) can silently truncate/fail on your hardest, longest examples — biasing your surviving sample toward easy questions. Check your context window against worst-case prompt length, not average.
- If your analysis code infers "what kind of record" it's looking at (e.g., "if it's a list of generations, majority-vote it"), a method whose defining step is *selection* (Best-of-N) can get silently mis-scored as a *counting* method. Cross-check aggregate numbers against a second, independently written analysis script.
- Bootstrap over questions only captures question-sampling variance, not seed/run-to-run variance for any stochastic method — treat significant results from single-seed runs as a lower bound on uncertainty, not the full picture.
- Watch position bias in model-as-judge/verifier steps (models often default to picking whichever candidate appears first) — this can masquerade as "reasoning" in your verifier when it's really just an ordering artifact.

**Toy walkthrough**
Say a question has 8 sampled solutions, 5 say "42", 2 say "41", 1 says "44". Majority vote picks 42 for free (just tally the extracted answers — zero extra tokens). Best-of-N instead pastes all 8 solutions back into a prompt and asks the model "which is best?" — costing one more full model call, and empirically, on <7B models, the model's pick agrees with the correct answer *less often* than the naive tally on the very cases where verifier and tally disagree (as low as ~10-20% correct-when-disagreeing, versus 50% needed for judging to break even). So you paid extra tokens for a worse answer.

**When not to bother**
- If you're on a 7B+ model and the choice is specifically Best-of-N-style self-verification, the gap between judging and counting was statistically indistinguishable from zero in this paper's data — plain majority voting is simpler and just as good, so don't build a verifier prompt for it.
- If your task is open-ended (summarization, prose, code style) where there's no clean majority to take, this whole comparison doesn't apply — you don't have a baseline to match against, and self-critique may genuinely be your best cheap option there.
- If your token budgets are trivial (single-digit calls, cheap enough that a 5-10x multiplier doesn't matter) and you're not trying to publish a comparative claim, this rigor is overkill — just use whatever's fastest to build; the statistical machinery here is for when you need to *claim* a method's mechanism (not just its budget) is responsible for a gain.
- If you have access to a *trained* verifier or reward model (not just prompting the same base model to judge itself), the paper notes trained verifiers do beat majority voting at comparable scale — the failure mode here is specific to untrained, same-model self-judgment.
