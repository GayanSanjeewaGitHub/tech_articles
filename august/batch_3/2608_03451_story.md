# SECTION 1 — The War Story

Grok-4.5 gets the fund-risk question right in every sense that matters. It finds the SQLite database, joins it against the JSON category map, extracts the PDF benchmark table, even watches the video for the drawdown alert. It computes the correct rows. Then it submits a table with five columns instead of six, and the grader marks it wrong.

That's the moment that should worry you. Not "the agent couldn't find the answer" — it found it. It just couldn't hand it back in the shape you asked for. Audit 136 of these failures and 52% trace back to exactly this: the right numbers, the wrong schema on the way out the door. Another 23% never even understood what "the answer" meant in the first place — wrong grain, wrong filter, wrong row count expected.

The naive assumption breaks here: everyone benchmarks agents on whether they can *find* and *compute* the right value. Almost nobody checks whether they can *materialize* it — reassemble scattered evidence, in the exact column contract the user specified, with nothing extra and nothing missing. Retrieval and reasoning get all the attention because they're where the interesting failures used to live. They aren't anymore.

**The bottleneck moved from knowing the answer to shipping the answer correctly formatted.**

The fix isn't a smarter retriever. It's a merciless grader: align columns by content, not header name; permute predicted columns against reference columns; canonicalize types, precision, units, order — then demand an exact match. Partial credit is banned.

```
for π in permutations(pred_columns):
    if canonicalize(pred[π]) == canonicalize(reference):
        return CORRECT
return WRONG  # even if 99% of values are right
```

Multimodal evidence and joins consistently drag accuracy down across every model tested — not because models can't read a PDF or a video, but because stitching six sources into one clean row is where discipline collapses.

If your eval only checks "did it get close," you're not measuring the thing that actually fails in production.

# SECTION 2 — Practical Implementation

## What you'd need

- **A pool of executable Text-to-SQL datasets** (the paper uses EHRSQL for clinical data and BULL for financial data) — anything with a real database, a natural-language question, and a gold SQL query that you can actually execute. This gives you ground truth "for free" via query execution rather than manual labeling.
- **An LLM for transformation work** (they use Qwen-Plus for cheap cross-language rewriting, Gemini 2.5 Pro + GPT-4o for document generation/validation, Claude Sonnet for video scripts) — none of this needs frontier reasoning models, it's generation + validation, so mid-tier models keep cost down (~$0.92/task for documents, ~$0.58/task for video, $0.0002/task for translation).
- **A relational DB engine** (SQLite is enough) to materialize task-local sampled databases.
- **Renderers**: CSV/JSON writers, a Markdown→PDF pipeline, and — only if you want the hardest tier — a video-generation stack (they use React/Remotion + TTS). You can skip video entirely for a v1.
- **A deterministic evaluator**: not an LLM judge. Pure code that does column-permutation matching + type/precision canonicalization + ordered/unordered row comparison.
- **Human reviewers** if you want benchmark-quality tasks — the paper uses 11 domain experts doing blind double-review with adjudication. For an internal eval, one careful reviewer per task is a reasonable minimum.

## Minimal version you could build yourself

1. **Pick a source of ground truth.** Take any database + query pairs you already trust (internal reporting SQL, a public Text-to-SQL dataset). Each gives you `(question, database, SQL, gold_result)`.
2. **Sample down to a task-local dataset.** Don't dump the whole warehouse into the workspace — extract a bounded set of tables/rows, but preserve foreign keys and any rows referenced by WHERE clauses/joins in the gold SQL (the paper's "constraint-aware sampling" — the point is: if you drop a row a filter depends on, the query silently returns nothing and your "gold" answer becomes wrong).
3. **Re-execute the SQL against the sampled data** to get the *sampled* gold answer — don't reuse the original answer, because sampling changes cardinalities and aggregates.
4. **Route each table to a rendering format** (CSV, JSON, a SQLite file, or — if you want difficulty — an LLM-written prose document that states the same facts in paragraph form, with an explicit rule: never invent values, mark or omit true nulls, keep an anchor/ID column stated in every paragraph so records stay joinable).
5. **Validate every rendering round-trips**: parse the CSV/JSON/PDF back out and diff it cell-by-cell against the source table before you trust it as a task artifact.
6. **Freeze an evaluation config per task**: for every gold column, record its semantic type (text/number/date/bool), numeric precision rule, and whether row order matters. Author this from the gold answer, not from any model's output.
7. **Build the deterministic evaluator** (the core reusable piece, independent of whether you ever build the rest):

```python
def evaluate(pred_csv, gold_rows, config):
    pred = parse_csv(pred_csv)
    if shape(pred) != shape(gold_rows):
        return False
    gold_canon = canonicalize(gold_rows, config)
    for perm in permutations(pred.columns):
        reordered = pred[:, perm]
        if not compatible(reordered, config):
            continue
        pred_canon = canonicalize(reordered, config)
        rows_match = (
            pred_canon == gold_canon if config.order_sensitive
            else multiset(pred_canon) == multiset(gold_canon)
        )
        if rows_match:
            return True
    return False
```

8. **Wire an agent harness against it**: give the agent only the question + a folder of files, no schema hints, force it to call `submit_answer(csv)`, and score with the function above. Track failure *stage*, not just pass/fail — was it the wrong data, the right data misfiled, or the right data with a wrong-shaped table?

## Where this fits in a pipeline

This isn't a production component — it's an **evaluation harness / regression gate** for anything you're calling a "data agent": a natural-language-to-report tool, an internal analyst-copilot, a multi-source QA system. It plugs in *before* you ship a new agent version or prompt/harness change: run it against a frozen task suite with the deterministic evaluator, and treat any score drop as a blocking regression the same way you'd treat a broken unit test. It replaces "eyeball a few outputs" and "ask an LLM judge if this looks right" — both of which the paper implicitly argues are too forgiving to catch the failure mode that actually dominates (column-shape errors), since an LLM judge would likely wave through 60 tasks where the values are correct but two columns are swapped or missing.

## Gotchas

- **LLM-judge evaluation hides the real failure mode.** If you grade with "does this look reasonable," you will never notice that 44% of your failures are "right data, wrong column count" (subtype M1 in the paper) — a bug an exact-match grader catches instantly and a semantic judge waves through.
- **Column-order independence is not optional.** If your evaluator requires predicted headers to match a fixed order, you're penalizing agents for restating the answer in a different but equally valid column order — that's not the failure you want to measure.
- **Row order matters only when the question asks for it.** Hardcoding order-sensitivity either way (always or never) will misgrade ranking questions or overgrade simple filters.
- **Numeric precision needs an explicit contract.** "12.8%" vs "0.128" vs "12.80" are three different string reps of one number — decide precision/units at task-authoring time, not grading time, or you'll get false negatives that look like model failures.
- **Sampling can silently break your own gold answer.** If you subsample a relational database for a workspace, re-execute the query on the sampled data — don't reuse the original full-database answer, it will no longer match.
- **Cross-modal tasks are disproportionately hard and disproportionately valuable.** The paper found multimodal tasks cost every model 1.8–14 points of accuracy and joins cost 9.7–19.8 points — if your real use case is single-source lookup, this whole heterogeneous-workspace setup is overkill.

## Toy walkthrough

Suppose your task is: "workspace" = one CSV of orders, one JSON of customer regions, one PDF containing a discount-tier table. Question: "For customers in the West region who ordered over $500, what tier discount applies and what's their order total after discount? Return customer, order total, tier, discounted total."

- Gold SQL-equivalent: join orders→customers on customer_id, filter region=West and total>500, join in tier from the PDF-derived table, compute discounted total.
- Gold answer: 3 rows, 4 columns, order matters = no (it's a filter+compute, not a ranking).
- Config: customer=text, order_total=number(2dp), tier=text, discounted_total=number(2dp).
- Agent submits a CSV with columns in the order (tier, customer, discounted_total, order_total) — evaluator permutes columns, canonicalizes numbers to 2dp, matches as an unordered row set, scores it correct even though the header order differs.
- Agent instead submits 5 columns (adds "region" nobody asked for) — automatic fail under shape-check, even if all 4 requested values are perfect. That's the point: the contract is exactness, not helpfulness.

## When not to bother

If your real system only ever answers questions against a single clean table (one database, no PDFs, no cross-source joins, no "return exactly these columns" contract), this entire apparatus is overkill. A simple Text-to-SQL benchmark with execution-based accuracy (Spider-style) gets you 90% of the value for a fraction of the engineering cost. Reach for the DataSpace-style heterogeneous-workspace + strict tabular-match setup specifically when your agent's job is to *reconcile evidence across formats and hand back a precisely-shaped table* — that's the exact capability this benchmark isolates, and it's expensive to build an eval harness for if you don't actually need to measure it.
