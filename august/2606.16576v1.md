# Can LLM Agents Infer World Models? Evidence from Agentic Automata Learning

## The Practical Problem

Companies are rapidly deploying LLMs as autonomous "agents" — systems that don't just answer a single question, but interact repeatedly with some environment (a website, a codebase, a database, a piece of software, a physical or simulated world) in order to figure out how that environment behaves, and then act correctly based on that understanding. The implicit assumption behind almost every agent product pitch is that the LLM, through enough back-and-forth interaction, will build an accurate internal "world model" of the system it's operating in — a correct mental map of its rules, states, and transitions — rather than just pattern-matching on the last few things it saw.

Nobody had a clean way to test whether that assumption is actually true, separate from all the confounding complexity of a real product. Web agents fail for a hundred reasons (bad selectors, flaky pages, ambiguous instructions); it's hard to isolate whether the failure is "the model can't build an accurate internal model of the system" versus "the interface was confusing." This paper strips the problem down to its purest form: can an LLM agent, given the ability to ask yes/no questions and to test hypotheses against ground truth, correctly reverse-engineer a hidden but well-defined system of rules?

A concrete real-world version of this: imagine an engineer being handed a legacy microservice or a third-party API with almost no documentation. They can only probe it — send a request, see what comes back, and occasionally check "does this endpoint behave the way I think it does?" against a sandbox. To fully understand it, they need to accumulate observations, form a working theory of how it routes/validates/rejects inputs, test that theory, and revise it when a counterexample proves it wrong — all without forgetting or contradicting earlier evidence. This is exactly the scenario a new hire or an on-call engineer faces with an undocumented state machine (e.g., an order-processing workflow, a permissions system, or a legacy billing engine with obscure edge-case rules). If you tasked an LLM agent with "figure out and document how this system behaves" by letting it poke at a sandbox version, would it actually converge on the truth, or would it convince itself of a plausible-but-wrong theory and stop?

## The Solution

The authors borrow a decades-old, rigorously studied framework from theoretical computer science called "active automata learning," and adapt it into a benchmark for LLM agents — they call it "agentic automata learning."

Here's the intuition. A deterministic finite automaton (DFA) is just a simple rulebook: a set of states, and rules for how each state changes based on the next input symbol, with some states marked "accepting." It's a clean stand-in for "a system with hidden internal logic that decides yes/no outcomes based on a sequence of inputs" — think of it as a tiny black-box vending machine that accepts or rejects a sequence of button presses depending on what state it's secretly in.

The agent is given two tools to probe this hidden machine:
1. **Membership Query** — "If I feed in this exact sequence, is it accepted or rejected?" (a single yes/no experiment)
2. **Equivalence Query** — "Here's my complete theory of how the whole machine works (my hypothesis DFA) — is it exactly right?" If wrong, the oracle doesn't just say "no," it hands back a specific counterexample sequence where the agent's theory and the real machine disagree — the single most informative kind of feedback you could get.

The agent's job: alternate between these two tool calls, accumulating evidence, until it can submit a hypothesis that is provably identical to the hidden machine, within a limited budget of queries.

Critically, there already exist classical algorithms (L* and TTT) that provably solve this task perfectly and efficiently — they're guaranteed to converge on the exact right answer in a bounded, predictable number of steps. That gives the researchers a mathematically optimal "ground truth" opponent to compare LLMs against, rather than just eyeballing whether an agent "seems" competent. They can also dial the difficulty up or down precisely, by controlling how many internal states the hidden machine has (harder machines need more probing to characterize).

To measure agents fairly, they track: (a) success rate — did the agent ever submit a truly correct final theory within budget; (b) efficiency — how many extra queries it needed compared to the optimal classical algorithm; and (c) two flavors of failure — "planning failures" (the agent simply never gathered enough evidence to know the answer, verified by checking that even a classical algorithm handed the same clues couldn't solve it) versus "reasoning failures" (the evidence was all there, but the agent failed to correctly piece it together into a right answer).

## How It Solves the Problem

Coming back to the undocumented legacy-system scenario: this benchmark is essentially a laboratory replica of exactly that situation, with one crucial addition — a ground truth referee. Just as the engineer would poke the real API and occasionally check "is my mental model of this workflow complete and correct?", the agent probes the hidden DFA with membership queries and periodically tests its full theory with equivalence queries.

The paper's findings tell you, concretely, what to expect if you handed this job to today's LLM agents. Performance is strong on small/simple systems (85% success for reasoning models on 4–5 state machines) but collapses on more complex ones (under 25% success once the system has 8–9 states) — meanwhile the classical, non-LLM algorithm solves every one of these perfectly, using far fewer probes. Translating that back to the API-reverse-engineering scenario: an LLM agent might genuinely nail a system with a handful of simple states/edge cases, but if you hand it a legacy system with a dozen or more interacting states, don't trust it to reliably surface the true logic — it is much more likely to: (1) fail to gather enough discriminating evidence in the first place (a "planning failure" — asking uninformative or redundant questions), or (2) gather enough evidence but reason inconsistently over it and land on a theory that actually contradicts something it already learned earlier (a "reasoning failure"). The paper directly measures this second failure mode as "non-informative queries" — the agent re-asking things it already knows the answer to, or proposing a theory it should already know is wrong given its own history — and shows this gets markedly worse the longer the interaction runs, which maps precisely onto the fear that an agent debugging a big legacy system for hours will start "forgetting" its own earlier findings and looping.

## Where to Apply This in the Real World

- **Reverse-engineering undocumented APIs, legacy systems, or third-party integrations** — exactly the scenario above, where an agent must build a correct behavioral model from black-box probing before it can be trusted to write documentation, generate client code, or safely automate against the system.
- **Automated protocol/format discovery** — inferring hidden validation rules, state machines in embedded devices, or proprietary file/network protocols through systematic probing (fuzzing-adjacent, but goal-directed rather than random).
- **Game AI / rules discovery** — agents that must learn the rules of a game or puzzle purely through play (a board game with unknown win conditions, a puzzle box).
- **Automated regression/spec testing** — an agent tasked with inferring "what does this legacy business-rule engine actually do" so it can be re-implemented or migrated, a very common and expensive real enterprise task.
- **Robotics/autonomous exploration** — the original motivating example from automata-learning theory: a robot exploring an unfamiliar environment through actions and sensor observations, building a map of "state transitions" it can trust.
- **Security testing/fuzzing with feedback** — probing an unknown system (e.g., an authentication or access-control layer) to characterize its accept/reject boundary, which is directly analogous to the membership/equivalence query structure.

## Where to Apply This in Real Software/Product/System Design

The deeper, reusable idea here is a **design pattern for building and evaluating any "agent that must learn a system through interaction rather than being told about it upfront."** Several things generalize well beyond DFAs:

1. **Give agents both a cheap "point query" tool and an expensive "full-theory check" tool.** The membership/equivalence query split is a great template for agent tool design generally: offer a fast, narrow probe (cheap, unambiguous) alongside a slower "submit your full hypothesis, get a maximally informative counterexample" tool. In practice this could mean designing a debugging agent that can both (a) run a small targeted check and (b) submit "here's my full understanding of the bug," with tooling that returns the single most useful failing case rather than a vague pass/fail.
2. **Build a "monotonicity"/consistency checker into your agent harness.** The paper shows the way to catch an agent going in circles is to check whether it ever contradicts its own prior findings, or repeats questions it should already know the answer to (their "non-informative query" metric). Any long-running agent system (support bots, coding agents, ops agents) can borrow this exact self-consistency audit as a cheap, automatic health signal — flag or halt an agent that starts asking questions whose answers are already implied by its own transcript.
3. **Separate "insufficient evidence" from "bad reasoning over sufficient evidence" when triaging agent failures.** The paper's planning-failure vs. reasoning-failure split (checked by running a classical/statistical algorithm over the agent's own collected evidence) is a general debugging technique: when your production agent fails a task, replay its transcript through a simpler, deterministic solver — if the simpler solver could have solved it from the same evidence, the bug is in the agent's reasoning/synthesis step, not its exploration strategy, and that tells your team exactly where to invest engineering effort (better retrieval/exploration prompts vs. better hypothesis-construction prompts).
4. **Use procedurally generated, complexity-controlled synthetic tasks as regression tests for agent capability.** Rather than relying on a fixed, hand-curated benchmark, the Boltzmann-sampling approach to generating DFAs at controlled complexity levels is a reusable idea for testing any agent capability at scale — e.g., generating synthetic state machines, config graphs, or decision trees of increasing size to continuously track whether a new model/prompt update actually improves an agent's ability to handle bigger, more complex systems before you ship it against real customer environments.
5. **Budget-aware agent evaluation.** The cost/runtime/token curves here (cost rising sharply, and non-linearly, with task complexity) are a cautionary template for any team estimating the true cost of "let the agent iterate until done" designs — worth building the same cost-vs-complexity dashboards before committing to open-ended agent loops in production.
