# Agentic Auto-Scheduling: An Experimental Study of LLM-Guided Loop Optimization

## The Practical Problem

Modern hardware is fast, but only if your code is written to exploit it. A loop nest doing matrix multiplication or a stencil computation can run 100x slower than it needs to, simply because it accesses memory in a cache-unfriendly order, fails to use available CPU cores, or misses opportunities to vectorize. Turning a naive loop into fast code requires applying the right sequence of transformations — tiling (blocking data to fit in cache), loop interchange (reordering nested loops), parallelization (splitting work across cores), unrolling, skewing (for wavefront-style dependencies), and fusion (merging loops to improve locality) — in the right order, with the right parameters (tile sizes, unroll factors).

This is genuinely hard. Compilers have polyhedral optimizers like Pluto that analyze dependencies mathematically and pick transformations using a cost model, and there are deep-learning-based "autoschedulers" trained to predict good schedules. But both rely on analytical proxies for performance rather than actually measuring it, so they can misjudge what's fast, especially on small problem sizes, and they generalize poorly outside the narrow class of programs they were designed or trained for. Meanwhile, hand-tuning loop nests requires expert compiler engineers who are expensive and in short supply, and there's a combinatorial explosion of possible transformation sequences to try.

Concrete scenario: A scientific-computing team maintains a library of dense linear algebra kernels (matrix multiplication, Cholesky decomposition, correlation/covariance computation) used in an HPC cluster. Their code runs correctly but slowly on a new 48-core server. They don't have a polyhedral compilation expert on staff, and running the existing autotuners either times out on some kernels (they only support rectangular loop nests) or produces underwhelming speedups because the built-in heuristics were tuned for a different generation of hardware. The team needs some way to systematically explore parallelization, tiling, and unrolling combinations, verify each is actually safe (won't silently produce wrong numeric results), and land on something measurably faster — without hiring a compiler specialist or spending weeks writing a custom search.

## The Solution

The paper's core idea, called COMPILOT, is deceptively simple: treat an off-the-shelf LLM (no fine-tuning, no special training) as a "pilot" that proposes optimization moves, while a real compiler with formal dependency analysis acts as the referee that checks whether each move is legal and how fast it actually runs. Neither the LLM nor the compiler works alone — they form a closed loop, like a chess player (the LLM) making moves against a rules-enforcing, score-keeping game engine (the compiler).

Here's how the mechanism works step by step:

1. **Briefing the agent.** At the start of a session, the LLM is given a system prompt that explains its job: it's a compiler optimization assistant. The prompt lists the available "moves" — nine transformation primitives (fusion, interchange, parallelization, 2D/3D tiling, unrolling, skewing, reversal, shifting) — with their exact syntax, describes the target hardware (CPU model, core count, cache sizes), and explains how to interpret error messages.

2. **Presenting the problem, anonymized.** The loop nest to optimize is shown to the LLM as annotated C code, with each computation block tagged with an ID (comp00, comp01, ...) so the LLM can address specific parts precisely. Variable and loop names are deliberately replaced with neutral labels (a, b, c, buf0, buf1) so the LLM can't be misled or biased by suggestive naming — it has to reason from structure alone.

3. **Forcing a "think first" step.** Before proposing anything, the LLM is asked to write a free-form analysis of the loop nest — what depends on what, which loops could parallelize, which look like reductions. This is a chain-of-thought step, and the paper shows experimentally that skipping it hurts performance by roughly 8-14%.

4. **The propose-check-execute-feedback loop.** The LLM then proposes a transformation sequence (e.g., "tile this loop, then parallelize the outer one") inside structured tags, along with its reasoning. A lightweight syntax checker filters out obviously malformed suggestions. Valid ones go to the real compiler (Tiramisu), which runs a rigorous polyhedral dependency analysis to determine if the transformation is *legal* — i.e., guaranteed not to change the program's meaning. Only the compiler, never the LLM, gets to decide correctness. If legal, the compiler actually generates and runs the transformed code and measures the real wall-clock speedup or slowdown.

5. **Feeding results back as memory.** Whatever happens — invalid syntax, illegal transformation, compiler crash, or a measured speedup/slowdown — gets reported back to the LLM in plain language, appended to the growing conversation. The LLM then uses that history (its "episodic memory") to decide its next move: abandon a failed direction, double down on something that worked, or try a variant.

6. **Stopping and repeating.** The LLM can declare it's done, though the framework nudges it to keep exploring if it stops too early (a common failure mode). Because LLM output is stochastic, running the whole dialogue several times and keeping the best result (a "best-of-5" strategy) reliably finds better schedules than a single run.

The crucial design choice is the division of labor: the LLM never writes actual optimized code and never gets to declare its own transformations safe. It only issues high-level, structured commands ("tile this, parallelize that"). The compiler is solely responsible for legality (via formal dependency analysis, not just "does the output look the same") and for producing the real optimized code. This sidesteps the classic risk with LLM-generated code — subtle correctness bugs that pass a quick output check but fail on different inputs. The paper actually measured this risk directly: when they let an LLM generate raw C code instead of issuing commands, about 18% of "seemingly correct, faster" results were later found to be silently wrong under different random inputs.

## How It Solves the Problem

Back to the HPC team stuck with slow linear algebra kernels on their new 48-core machine: instead of hiring a polyhedral-compilation expert or manually trying tiling/parallelization combinations by hand, they'd hand each kernel to COMPILOT. The framework anonymizes the loop, asks a general-purpose LLM (the paper used models like gemini-2.0-flash or gpt-4o, nothing specialized) to analyze it, and lets it iteratively propose transformations. For something like a large correlation-matrix kernel, the system discovered — completely on its own, through trial and error — a combination of aggressive outer-loop parallelization plus tiling and unrolling that yielded a 339x speedup over the naive version, and it did so with zero risk of silently corrupting results, because every proposed schedule was checked by Tiramisu's formal dependency analysis before being trusted. For smaller kernels, it instead found that locality-improving transformations like tiling alone or skewing worked better than parallelism — an adaptive judgment call that a size-agnostic classical optimizer (like Pluto) often gets wrong, sometimes even making things slower on small inputs. Because the team can also run the process five times and keep the best schedule (best-of-5), they get, on average, a 3.5x average speedup over the original code and outperform the state-of-the-art Pluto optimizer overall — all without touching the code by hand or trusting an unverified AI-generated rewrite.

## Where to Apply This in the Real World

- **HPC and scientific computing pipelines**: numerical libraries (BLAS-like kernels, stencil computations for physics/climate simulation, linear solvers) that need to be re-tuned whenever they're ported to new CPU/GPU hardware generations.
- **Machine learning kernel engineering**: optimizing custom tensor operations (convolutions, attention kernels) for new accelerators, where hand-tuning for cache and core layout is a major bottleneck, similar in spirit to what TVM/Halide autoschedulers already attempt but with execution feedback instead of a learned/static cost model.
- **Cloud cost optimization**: enterprises running large batch or scientific workloads on cloud VMs, where a 2-3x speedup translates directly into lower compute billing, achieved via automated re-optimization rather than manual DevOps effort.
- **Legacy code modernization**: organizations with old Fortran/C scientific codebases that were never optimized for modern multi-core, multi-cache architectures, where no team member has deep compiler expertise anymore.
- **Compiler and toolchain vendors**: embedding an LLM-guided exploration mode alongside existing heuristic optimizers (GCC/LLVM pass selection, autotuning frameworks) as a complementary strategy, particularly useful for edge cases where static heuristics misjudge performance.

## Where to Apply This in Software/Product/System Design

The generalizable pattern here is: **"LLM proposes, deterministic system verifies and measures, feedback closes the loop."** This is a design pattern worth lifting out of the compiler domain entirely. Any situation where you want an LLM to explore a large combinatorial search space of *risky, hard-to-verify-by-eye* actions — but where you have (or can build) a fast, authoritative checker plus a real measurable outcome — can use this same architecture:

- **Database query optimization**: an LLM proposes index changes, join reordering, or query rewrites; a query planner/EXPLAIN-based cost estimator and actual execution-time measurement serve as the "compiler," rejecting invalid rewrites and reporting real latency deltas back to the LLM for the next iteration.
- **Infrastructure-as-code / cloud configuration tuning**: an LLM suggests changes to autoscaling policies, resource limits, or caching layers; a validator checks the config against policy/schema constraints and a canary deployment reports real latency/cost metrics back as feedback, closing the loop the same way COMPILOT closes it with speedup numbers.
- **Automated A/B experiment design**: an agent proposes variants of a pricing rule or ranking heuristic; a simulator or shadow-traffic system checks for legality (business rule violations) and reports real conversion metrics, letting the LLM refine its next proposal.
- **Security hardening / firewall rule tuning**: an LLM proposes rule changes; a policy checker verifies they don't violate compliance invariants, and a staging environment measures whether they actually block the intended traffic without breaking legitimate flows.
- **General agentic coding assistants**: rather than having an LLM directly emit a risky refactor as raw code (which is hard to verify for correctness), have it emit *structured, composable commands* over a constrained API (like "rename symbol X", "extract method Y", "reorder these two statements") that a static analyzer or type checker can validate before ever touching the codebase — mirroring COMPILOT's insight that structured, checkable actions dramatically reduce the correctness risk versus direct code generation, and cut token cost roughly 5x in the process.

The key architectural takeaways to carry over: (1) constrain the LLM's action space to a small, composable vocabulary of operations rather than free-form output, (2) never trust the LLM's own claim of correctness — delegate verification to a formal or authoritative checker, (3) always ground the next decision in real measured outcomes rather than a static proxy score, and (4) exploit the LLM's stochasticity deliberately via multiple independent runs, since diminishing but real returns come from exploring several independent trajectories rather than one long one.
