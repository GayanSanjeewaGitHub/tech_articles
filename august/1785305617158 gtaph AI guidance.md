# Graph Engineering for Multi-Agentic Systems: The Andrew Ng Playbook

## The Practical Problem

Large language models are surprisingly weak when asked to produce a good result in a single pass, and the reason is not lack of capability but lack of process. Andrew Ng's own benchmark data makes this vivid: GPT-3.5 answering coding questions zero-shot (one prompt, one answer, no revisions) solves only 48.1% of the HumanEval benchmark. GPT-4, a materially more powerful model, only reaches 67.0% zero-shot. But when the *weaker* GPT-3.5 model is wrapped in an agentic workflow — allowed to draft, get critiqued, and revise — its score jumps to 95.1%, blowing past the more advanced model used naively. The core problem the paper addresses is this: teams keep trying to solve reliability problems by upgrading the model, when the real lever is the surrounding architecture — how the model iterates, uses tools, plans, coordinates with other model instances, and remembers things across time.

As systems get more ambitious, a second, deeper version of this problem appears. A single-agent loop (draft → critique → revise) works fine as long as everything fits in one context window and the task lives inside one session. But once you have multiple specialized agents (a researcher, a coder, a reviewer, a security auditor) that need to share facts, and once work needs to persist and be explained across days, weeks, or thousands of related tasks, simply passing conversation transcripts between agents breaks down. The orchestrator agent becomes a bottleneck — its context window fills with summaries of summaries, detail gets lost, and nobody can explain after the fact *why* the system produced a particular answer.

**Concrete real-world scenario:** Imagine an engineering team building an AI code-review assistant. Day one, they just prompt an LLM: "review this code for bugs." It catches some real issues and also confidently praises broken code — accuracy hovers around 55%. As the team scales this to reviewing hundreds of pull requests a week with multiple specialized checks (security review, style review, test coverage review), they run into two separate walls: (1) a single review pass is unreliable and they don't know how to systematically improve it, and (2) once they add a security-focused agent alongside the general reviewer, someone has to reconcile both agents' findings, and nobody has a record of "we saw this exact vulnerability pattern in this file three months ago" — every PR review starts from zero, so the same class of bug gets rediscovered (or missed) over and over. This is a scenario any engineering manager running an AI-assisted dev tooling initiative will recognize almost immediately.

## The Solution

The paper's answer is not a single algorithm but a **vocabulary of composable design patterns** that graduate a system from "one dumb LLM call" to "graph-grounded multi-agent system," with a clear rule for when to add each layer of sophistication.

Think of it like the evolution of how a human team gets work done:

1. **Reflection (a person re-reading their own draft).** One LLM call produces a draft. A second call — acting as a critic — compares the draft against an explicit rubric and lists concrete defects. A third call revises the draft based on that critique. This loop repeats up to a capped number of iterations. The key mechanical insight: separate *critiquing* from *rewriting* — never ask a model to "just improve this," because that produces an opaque replacement you can't audit. Force the critic to output a structured list of specific issues first, then feed that list into a distinct rewrite step, and log every draft/critique/revision so failures can be diagnosed.

2. **Tool Use (a person looking things up instead of guessing).** The model is given access to external capabilities — web search, code execution, a database query — and decides for itself when to invoke them. This turns the LLM from a closed box reciting parametric memory into something that can check its claims against reality: run the code to see if it actually works, search to verify a fact. Guardrails matter here: validate tool arguments before calling, don't blindly trust tool output, separate read permissions from write permissions, and cap the number of tool calls to avoid infinite loops.

3. **Planning (a person making a to-do list before starting a big task).** For complex, multi-step objectives, the model first writes an explicit plan (a structured list of steps) before executing anything. Critically, if a step fails partway through, the agent "replans" but preserves everything that already succeeded — it doesn't throw away steps 1–4 just because step 5 failed. This prevents wasted work and wasted tokens.

4. **Multi-Agent Collaboration (a team with different specialists instead of one generalist).** Multiple LLM instances, each given a different role prompt (coder, reviewer, tester, security auditor), work on the same problem and communicate through structured "artifacts" (typed outputs like "here are the defects I found" or "here is the code and my assumptions") rather than open-ended chat transcripts. The logic is that different role framings surface different classes of errors — a coder optimizes for functionality, a security reviewer assumes every input is hostile — so several narrow specialists catch more than one generalist rereading the same thing three times.

5. **The Graph (a shared, persistent notebook the whole team can read and write to).** This is the paper's headline addition. Instead of agents passing giant conversation transcripts through a central orchestrator (which becomes a bottleneck as team size grows — 10 workers means 10 outputs the orchestrator must somehow digest), all agents read from and write to a shared **knowledge graph**: entities (people, files, concepts) as nodes, typed relationships (e.g., "found_in," "supports," "contradicts," "supersedes") as edges, and every claim carrying **provenance** — a record of which source or run produced it. Corrections are never silent overwrites; instead a new version is written and linked back to the old one with a "supersedes" edge, so the full history is always inspectable. The orchestrator's own context stays small because it queries the graph for what it needs rather than holding everything in its prompt.

Ng frames the progression as an "externalization of cognition": a loop externalizes revision, a chain externalizes task order, a network externalizes role specialization, and a graph externalizes shared state and relationships. Each stage is added only when the previous stage's specific, measured failure demands it — not proactively, because every added pattern also adds cost, latency, and a new way to fail.

## How It Solves the Problem

Go back to the code-review assistant. Applying this playbook produces the exact staged improvement the paper documents as a worked example:

- **Day 0 (zero-shot):** "Review this code" → free-form paragraph, 55% accuracy, sometimes praising buggy code.
- **Day 1 (add reflection):** A second call asks "did you cite line numbers, did you assign severity, revise" — pushing accuracy to 72% by forcing specificity instead of vague impressions.
- **Day 2 (add tool use):** The reviewer agent actually runs the test suite and reads linter output instead of guessing whether code works, citing real test failures — 84% accuracy.
- **Week 1 (add planning):** For large pull requests, the agent writes a plan ("check security-sensitive files first, then business logic, then tests") so each section gets a focused, appropriately-tailored review instead of one generic pass — 79% on large PRs (up from 61% with reflection alone).
- **Week 2 (add multi-agent):** A dedicated security-auditor agent runs alongside the general reviewer and catches injection vulnerabilities the generalist missed — combined accuracy 88%.
- **Month 1 (add the graph):** Every finding — a vulnerability, the code pattern that caused it, the file it was found in — is stored in the graph with typed edges like `found_in`, `similar_to`, `fixed_by`. Now, when a *new* PR touches a file that previously had a known vulnerability, the reviewer agent queries the graph and flags the recurring pattern automatically — accuracy on repeat patterns reaches 95%. The team no longer starts every review from zero; institutional knowledge accumulates across hundreds of PRs in a form no single context window could ever hold, and any flag can be traced back to exactly which prior PR and commit produced it.

This directly resolves both original pain points: the unreliable single-pass review is fixed by reflection plus tools, and the "we keep rediscovering the same bug with no memory" problem is fixed specifically by the graph, which gives the system durable, queryable, provenance-backed memory that persists across every future PR review, not just the current session.

## Where to Apply This in the Real World

- **Software engineering tooling:** automated code review, security auditing, and technical debt tracking that accumulates institutional memory across a codebase's history (the paper's own worked example).
- **Customer support / operations:** routing tickets to specialized agents (billing vs. technical), with a graph tracking recurring customer issues, prior resolutions, and escalation history so agents don't re-solve the same root cause repeatedly.
- **Research and knowledge work:** a "research agent" that Ng himself uses personally — sending open research questions off to be investigated while doing other work, with findings (claims + sources) stored so that later queries can build on prior findings instead of re-researching from scratch.
- **Compliance, legal, and financial review:** high-stakes document review (contracts, filings, transactions) where an evaluator-optimizer loop with explicit gates is required, and where the audit trail (provenance, versioning) is not a nice-to-have but a regulatory necessity.
- **Enterprise knowledge management:** any organization that wants an AI layer over its internal documents, tickets, and decisions where facts need to persist, be cross-referenced by multiple teams/agents, and be explainable ("why did the system flag this?").
- **Manufacturing/ops incident diagnosis:** multi-agent systems where a diagnostic workflow, a planning agent, and historical incident graphs combine to recognize recurring failure patterns across equipment or processes.

## Where to Apply This in Software/Product/System Design

This paper is really offering a **design-pattern ladder** that generalizes well beyond LLM coding assistants — it's a template for building any system that must get more reliable and more stateful over time without a rewrite:

- **Treat "add a critique step" as a cheap, universal reliability upgrade.** Any pipeline that produces free-form output (report generation, summarization, content moderation, customer-facing copy) can borrow the reflection pattern: generate → evaluate against an explicit rubric → revise, with a hard iteration cap and full logging of every intermediate artifact for debuggability. This is the paper's "highest ROI, lowest cost" recommendation and should usually be the first thing added to any existing LLM feature before reaching for anything fancier.
- **Design typed "artifact contracts" for every hand-off between components, not just between agents.** Whether it's microservices, pipeline stages, or agent hand-offs, the paper's insight — pass a validated, typed, bounded summary rather than an unbounded raw transcript/log — is a general architecture principle for avoiding "context bottleneck" failure modes (the same failure mode as an overloaded message queue consumer or an API gateway forced to buffer entire request histories).
- **Use the loop → chain → network → graph decision framework as a system-design checklist**, independent of LLMs: ask "does this system need cross-session state, do multiple independent workers need to share facts without a central bottleneck, and must results be explainable after the fact?" If yes to any of these, the answer is a shared, durable, provenance-tracked store (a graph, an event-sourced log, or an audit-friendly database) rather than in-memory or in-transcript state. This reframes "should we add a database/graph layer" as a measurable engineering decision (Rule 5: "the graph earns itself" — only add it when the same entity is queried by more than one consumer or session) rather than a speculative architecture choice.
- **Apply "count tokens/cost, not components" as a general resource-budgeting discipline.** The paper's Rule 4 — a 3-agent system costing the same as 1 agent running 3x longer — generalizes to any distributed system: budget by actual resource consumption (compute, API calls, dollars) rather than by counting how many services/agents/microservices exist. This helps product teams avoid "premature multi-agent" over-engineering the same way engineers avoid premature microservice decomposition.
- **Build provenance and versioning into any system that must explain itself later** (e.g., recommendation engines, fraud-detection flags, automated decision systems): store not just the current answer but a traceable chain of "task → plan → artifact → source → evaluator decision → execution record," using additive/superseding writes rather than silent overwrites. This is directly reusable as a general auditability pattern for any AI-assisted or automated decision pipeline that regulators, customers, or engineers might later ask "why did it do that?"
