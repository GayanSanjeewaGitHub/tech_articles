# Flyte 2.0: The Orchestration Stack for Durable, Self-Healing Production Agents

## 5 Intuitive Takeaways

1. **The real bottleneck for production agents isn't prompt engineering — it's infrastructure failure wiping out agent state** — agents fail at multiple layers: infrastructure (OOM kills, spot instance preemption), network (timeouts, outages), logical (bad tool arguments), and semantic (hallucinations). Most eval harnesses only test semantic correctness. But in production, a spot instance disappearing mid-run destroys all hard-earned context, and the agent has to restart from scratch. Durability — the ability to resume exactly where you left off — is the unsexy capability that separates demos from production.

2. **Three building blocks make agent failure cheap: replay logs, global caching, and intermediate state persistence** — a replay log records every step and output at granular level, so a crashed agent skips completed steps and resumes from the failure point (critical for 200+ step runs). Global caching shares expensive IO-bound and LLM call results across all agent runs (same prompt = same web search result, no re-payment). Intermediate state persistence automatically serializes every LLM output and tool call result to object store, giving you data lineage and crash recovery for free.

3. **Infrastructure failures are context, not just errors — agents can self-heal if you surface system-level information into their loop** — when an agent gets an OOM error, most systems just crash. But if you catch that exception and feed it back into the agent's context, the agent can reason about it: "I need more memory for this training job" and provision larger resources in its next iteration. The key insight is that context engineering isn't just about tokens and RAG — it's also about making infrastructure state visible to the agent so it can adapt.

4. **Sandboxed code generation (code mode) replaces bloated tool-call formatting with pure Python orchestration** — instead of the agent formatting JSON arguments for predefined tools, you give it a toolbox and let it write sandboxed Python code that composes those tools directly (no IO, no network, pure function calls). This eliminates context bloat from tool schemas, gives the agent more flexibility in orchestration logic, and creates a tight error-iteration loop where the agent fixes its own code bugs. For tasks where no existing tool fits, a stateless code sandbox lets the agent write and run arbitrary code with controlled permissions.

5. **Start with one agent and one sub-agent layer — four-tier hierarchies are the upper extreme, not the norm** — a real-world case study (Dragonfly, 250K SaaS products, 200 steps and 100 LLM calls per product) required a four-tier architecture: driver → coordinators → researchers → tools. But this is the upper bound. The coordinators existed specifically to detect and consolidate duplicate research threads via semantic convergence. For most use cases, a single agent with tools — or one agent with one sub-agent layer — is sufficient. The "butter robot" principle: build agents that do one thing well, and only add orchestration tiers when you empirically hit resource contention or duplicate work.
