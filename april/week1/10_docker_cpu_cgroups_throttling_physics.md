# The Physics of Docker CPU Allocation — Cgroups, CFS, and the Throttling You Don't See

## Intuitive Takeaways (3 Key Points)

- **`--cpus=1.5` is not "one and a half processors" — it's a time quota** — When you set `--cpus=1.5`, Docker writes a cgroup property: `cpu.max = 150000 / 100000`. This means every 100ms window, your container gets 150ms of CPU time (achievable across multiple cores). If your threads exhaust that 150ms budget before the window closes, the cgroup **freezes every thread in the container** until the next 100ms window opens. This is why containers feel mysteriously slow — it's not your code, it's involuntary throttling. Your threads are literally frozen mid-execution, waiting for their next time slice. Without any CPU limit, containers run on a fair-share basis (`cpu.shares`), competing with all other processes without hard caps.

- **CPU-set pinning (`--cpuset-cpus`) exists for NUMA-aware workloads, and it changes everything for stateful services** — Beyond throttling, you can *dedicate* specific physical CPU cores to a container (e.g., `--cpuset-cpus=0,1`). This matters because of NUMA (Non-Uniform Memory Access) — CPUs access local memory faster than remote memory on multi-socket machines. When a database like Postgres, Kafka, or Redis runs inside a container, pinning it to cores on the same NUMA node means memory access stays local and fast. Without pinning, the OS scheduler can bounce your threads across NUMA nodes, silently doubling memory latency. So there are three escalating levels: no limit (fair share) → `--cpus` (throttled quota) → `--cpuset-cpus` (dedicated hardware pinning with NUMA locality).

- **Multi-threaded apps (Java) benefit from more CPUs; single-threaded apps (Node.js) do not — and misunderstanding this wastes real money** — If your container runs 100 threads (Java, Go) with `--cpus=1.5`, those threads must share the 150ms quota via CFS (Completely Fair Scheduler) in a round-robin. Thread T1 runs for 10ms, T2 takes 80ms and gets frozen when the window expires, then resumes next window — creating visible latency. Giving 4 CPUs means multiple threads can execute *simultaneously* across cores, dramatically reducing wait time. But for a traditional single-threaded Node.js app, giving 2 CPUs instead of 1 does **not** halve a 20-second task to 10 seconds — there's only one thread of execution, so the extra CPU sits idle. You pay for cores your runtime physically cannot use. The fix for Node is `cluster.fork()`, not more CPUs.
