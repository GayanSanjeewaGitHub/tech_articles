# Designing a Stock Broker Platform: System Architecture for Real-Time Trading

**Intuitive Takeaways (5 Key Points)**

- **The system has a split personality — reads demand availability, writes demand consistency:** Viewing stock prices is a read-heavy, availability-first path (users must always see *something*, even if slightly stale). Placing buy/sell orders is a write path that demands strict consistency and ACID compliance (you cannot lose an order or deduct money without confirmation). This duality means the two flows require fundamentally different infrastructure: a time-series DB with SSE push for prices, and a transactional RDBMS with Kafka-backed async processing for orders. Designing them identically would compromise both.

- **Server-Sent Events (SSE) over WebSockets for price streaming — because the communication is one-directional:** The client subscribes to a stock symbol and then only *receives* price ticks; it never sends data back on the same channel. WebSockets would be overkill (maintaining full-duplex connections per stock per user drains client resources). SSE gives you a lightweight persistent connection where the server pushes updates. The same logic applies server-side: the exchange pushes price ticks to the exchange gateway processor via SSE, avoiding expensive polling of an already-overloaded exchange.

- **The exchange gateway processor is the critical boundary — it isolates your system from an external authority you don't control:** The exchange is a third-party system with its own rate limits, pricing, and contracts. Every interaction with it costs money and adds latency. So the architecture wraps all exchange communication behind a single gateway processor that: (1) subscribes to price feeds and writes them to a time-series DB so clients never hit the exchange directly, (2) drains orders from Kafka one-by-one to apply backpressure instead of flooding the exchange, and (3) receives order status updates via webhooks so you don't need to poll. This boundary converts an unpredictable external dependency into a controlled internal flow.

- **Kafka between order placement and exchange submission is the backpressure mechanism that prevents system collapse during surges:** Market open (9:15 AM) and market close (3:30 PM) produce massive order spikes. Without a buffer, the exchange gateway would either drop orders or overwhelm the exchange. Kafka absorbs the burst — OMS writes orders to the order DB (status: pending), publishes to Kafka, and the gateway processor consumes at a controlled rate. Failed orders get retried; permanently failed ones land in a dead letter queue for manual intervention. The exchange returns an `exchange_order_id` on acceptance; absence of that ID after retries signals the order never reached the exchange.

- **Co-location and hybrid scaling are the latency weapons for financial systems:** Unlike typical web apps where CDNs solve latency, a stock broker's critical path is between *your servers and the exchange*. The architectural move is physical: place your infrastructure in the same data center (or at minimum the same region) as the exchange, ideally with direct wired connections. On the scaling side, a pure auto-scaling strategy is too slow for trading spikes — pre-provision warm servers for high-volume symbols and hedge fund clients, and use hybrid load balancing that routes all traffic for a hot symbol (e.g., top Nifty 50 stocks) to dedicated oversized instances rather than distributing it evenly.
