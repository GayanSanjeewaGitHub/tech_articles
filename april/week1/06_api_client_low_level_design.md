# Designing an API Client: The Hidden Complexity Behind "Just a cURL Wrapper"

**Intuitive Takeaways (5 Key Points)**

- **Variable interpolation is not string replacement — it's a scoped resolution engine with precedence rules:** Variables exist at four layers: global, environment (dev/staging/prod), collection, and runtime (session-only). Resolution follows strict precedence: runtime > collection > environment > global. Each variable has an *initial value* (synced to cloud/team) and a *current value* (local-only, never leaves your machine). This separation is a deliberate security and collaboration design — secrets and overrides stay local, defaults propagate across the workspace. The data model stores scope, key, initial value, current value, and an `is_secret` flag for masking sensitive data.

- **Request chaining turns a stateless HTTP tool into a stateful execution pipeline:** The output of request 1 (e.g., a JWT token from an auth endpoint) must be usable as input to request 2. This is implemented via a shared environment object on the core runtime object (e.g., `rq.environment`). Each request's post-response script can *push* values into this shared environment, and subsequent requests *pull* from it during variable resolution. The "environment" here is not just config — it's mutable shared state across an execution chain, which is why execution order matters and why collection runners execute sequentially.

- **Collection runs require a surprisingly deep relational schema:** Running a collection means executing every request in order — including pre-request scripts, variable resolution, the HTTP call, post-response scripts, and test assertions — then storing granular results. The data model chains: **Collection → Collection Run** (which environment, how many iterations, pass/fail status) **→ Run Result per request** (response time, status code, response body/headers, pass/fail). Each request itself stores a URL *template* (not a URL — it contains variable placeholders), headers/params as JSON with variable references, body type, and auth config. Scripts are stored separately with a phase field (`pre-request` or `post-response`) and a timeout to prevent infinite loops.

- **The test assertion framework is baked into the execution pipeline, not bolted on after:** Test cases are named groups of assertions (e.g., "user should have required fields") stored as source code per request. They run automatically during post-response execution, piggybacking on a familiar assertion library (like Chai.js) with injected context (`rq.response`). If any assertion fails, the request is marked failed. The architectural insight: this catches backend contract changes (e.g., a missing field in the response) at the API client layer *before* they reach production — making the API client a lightweight contract testing tool, not just a manual testing UI.

- **The scripting runtime is the hardest unseen problem — it's an isolated, pre-loaded JavaScript sandbox:** Every pre-request and post-response script runs in an isolated environment that cannot corrupt the host application. It must pre-load the `rq` object (with request, response, environment, globals), support built-in libraries (e.g., Lodash, Moment), allow importing external JS libraries, enforce timeouts, and still provide full access to shared state for request chaining. This is effectively a sandboxed JavaScript VM embedded inside the client — far from "just running a script." It's the single component that makes everything else (variable resolution, chaining, assertions) programmable rather than declarative.
