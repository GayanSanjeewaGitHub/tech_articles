# Top K Heavy Hitters: Designing Real-Time Ranking Over Massive Event Streams

**Intuitive Takeaways (5 Key Points)**

- **The core problem is not sorting — it's maintaining approximate rank over an unbounded, high-throughput stream:** With 10 billion song plays per day (~100K events/second) across 100 million songs, you cannot sort on demand. The architecture must continuously aggregate counts and maintain a min-heap of size K (e.g., 1,000). A min-heap is used — not a max-heap — because you need to efficiently evict the *smallest* count whenever a new song exceeds it. The heap always holds exactly the top K; everything else is discarded. Sorting the final K elements is trivial.

- **Flink solves time-windowed ranking out of the box; building it yourself means managing dual Kafka pointers:** For "all-time top K," a simple hashmap + heap suffices. But for "top K in the last hour," you need a sliding window — counts must be *decremented* as old events expire. Flink handles this natively with built-in windowing and state management. Without Flink, you simulate it using two Kafka consumer pointers: one at the head (incrementing counts for new events) and one offset by the window duration (decrementing counts as events age out). Each time window requires its own hashmap and heap — multiplying state and complexity.

- **Horizontal scaling requires partitioning by song ID, which forces a merge layer:** A single worker can't handle 100K events/sec, so you partition Kafka by song ID and assign each partition to a dedicated worker. But now each worker only knows the top K from *its* subset of songs. A separate **Top-K aggregation service** must merge these partial heaps — essentially solving the "merge K sorted lists" problem — before writing the final global top K to Redis for client reads. Partitioning solves throughput but introduces a coordination layer that didn't exist in the single-node design.

- **Snapshotting is what decouples Kafka retention from all-time correctness:** You can't keep Kafka retention at "forever" — storage would explode. But if a worker crashes and restarts, it needs the all-time counts to resume correctly. The solution: periodically snapshot (checkpoint) the current hashmap state to a database. New or recovering workers load the snapshot first, then resume consuming from the Kafka offset at which the snapshot was taken. This is the same pattern Flink uses internally for fault tolerance — you're just building it manually.

- **The 100ms read latency target is achieved by pre-computing results into Redis, not by querying on demand:** The client never triggers aggregation. Workers continuously process the stream, maintain heaps, and periodically (e.g., every 60 seconds) flush the current top K to Redis. The client's GET request simply reads from Redis — a sub-millisecond operation. This separation of the write path (stream processing, aggregation, heap maintenance) from the read path (Redis lookup) is what makes low-latency feasible despite the massive event volume. The trade-off: results can be up to ~60 seconds stale, which the requirements explicitly allow.
