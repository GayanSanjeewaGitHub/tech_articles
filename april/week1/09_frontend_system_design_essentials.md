# The Physics of Front-End System Design — 14 Concepts Distilled

## Intuitive Takeaways (5 Key Points)

- **Rendering strategy is the first architectural decision, not a framework default** — There are five distinct rendering strategies (SSG, ISR, SSR, CSR, Partial Pre-rendering), and each sits on a spectrum trading off build-time cost against request-time freshness. Static site generation pays the cost once at build and delivers the fastest client load; server-side rendering pays per request but handles dynamic content; client-side rendering ships an empty shell and offloads everything to the browser. The architectural insight: choosing wrong here compounds into every performance problem downstream — you cannot optimize your way out of a fundamentally mismatched rendering model.

- **Micro-frontends solve deployment risk, not code organization** — As a frontend grows, the real danger isn't messy code — it's that every deployment ships the entire monolith, so a one-line change can break everything. Micro-frontend architecture (via Webpack 5 Module Federation) splits the app into independently deployable units, each with its own rendering strategy — SSG for product pages, SSR for checkout, CSR for chat. The key mental model: micro-frontends are a deployment boundary pattern, not a file-organization pattern.

- **Performance optimization follows a strict sequence: measure → prevent re-renders → lazy load → shrink bundles** — You cannot optimize what you haven't profiled (Chrome DevTools Performance tab, React Profiler). The biggest killer is unnecessary re-renders — a parent re-render cascades to all children unless blocked by `React.memo`, `useCallback`, or `useMemo`. After that, lazy loading defers component hydration until user interaction (e.g., charts load only on click). Finally, tree-shaking strips dead code and bundle splitting reduces initial payload. This is a layered defense — each layer addresses a different bottleneck in the rendering pipeline.

- **Client-side caching is an API call elimination strategy, not just a speed trick** — The pattern: intercept every server response, store it in local state management, and on mutations (delete, update, create) modify the cache directly instead of re-fetching. React Query adds expiration-based staleness (`staleTime`) so data auto-refreshes after a TTL. GraphQL further reduces payload size by letting the client specify exactly which fields it needs (eliminating over-fetching) and Apollo Client adds its own in-memory cache keyed by query + variables. Debouncing on the client side (e.g., 500ms delay on search keystrokes) is the final layer — it's rate-limiting before requests even leave the browser.

- **Pagination is a consistency trade-off: offset gives random access, cursor gives stable windows** — Offset pagination (`OFFSET + LIMIT`) lets users jump to any page but breaks when rows are inserted or deleted between pages — items shift forward or duplicate. Cursor pagination (sequential ID or timestamp as a bookmark) gives stable results immune to concurrent mutations and is cheaper on the database (seeks directly to the cursor instead of scanning skipped rows), but sacrifices the ability to jump to page N. The choice maps directly to your data's mutation frequency: high-churn data demands cursors; low-churn, user-navigable data tolerates offsets.
