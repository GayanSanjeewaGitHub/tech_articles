# Top K YouTube Videos: From Naive SQL to Approximate Streaming at Scale

**Intuitive Takeaways (5 Key Points)**

- **Start with a naive working system, then optimize — this is the interview strategy and the production strategy:** Begin with a Kafka topic of video views, a consumer that writes per-view counts to a Postgres table, and a SQL query (`ORDER BY views DESC LIMIT K`) with an index on views. This works for all-time top K but collapses for time-windowed queries (last hour/month) because you'd need to scan, aggregate, and sort hundreds of gigabytes of hourly-grain rows on every read. Recognizing *where* the naive design breaks is more valuable than jumping to the optimal design.

- **Pre-aggregation at multiple time grains eliminates expensive read-time computation:** Instead of storing only hourly view counts and aggregating them into days/months at query time, have Flink write to separate tables for each granularity (hour, day, month, all-time) as views arrive — 3x the writes, but each table can be indexed on views so that the top K query becomes a near-constant-time B-tree lookup instead of a full-table scan + sort. The cron that populates the Redis cache now runs a trivial query instead of processing hundreds of GB.

- **Sliding windows are fundamentally harder than tumbling windows — and the difference is worth negotiating in requirements:** A tumbling "last month" window resets on fixed boundaries (one window per month). A sliding "last month" updates every minute (thousands of overlapping windows). The sliding window trick: maintain minute-grain counts, and for each new minute, add the new minute's views and subtract the views from the minute that just fell off the window edge. This avoids recomputing from scratch but multiplies writes and requires minute-level storage. Show the cost to your interviewer — then suggest tumbling for coarse windows (month) and sliding only for fine ones (hour).

- **Count-Min Sketch + sorted set is the approximation play that trades precision for massive resource savings:** A Count-Min Sketch is like a Bloom filter for counts — it remembers how many times it's seen an identifier using hashed counters, with known error bounds and dramatically less memory than a full hash table. Pair it with a small sorted set (e.g., 5,000 entries in Redis) that only tracks items whose counts exceed the current top-K threshold. On each view: increment the sketch, query the approximate count, update the sorted set if the count is competitive. The entire system fits in memory, avoids the views database entirely, and handles sliding windows by decrementing expired events. Use this to impress — but only after you've shown the exact solution first, because interviewers may not be familiar with it.

- **The real skill is understanding data flow, not memorizing technologies:** Flink, TimescaleDB, ClickHouse, Prometheus — each subsumes parts of the problem (windowing, aggregation, time-series storage), but interviewers care about *why* those capabilities exist, not that you can name them. The transferable insights are: partition by entity ID to scale writes, pre-aggregate to avoid read-time computation, cache pre-computed results with TTLs tied to your staleness SLA, checkpoint state so workers can recover without replaying the entire stream, and use heaps (min-heap of size K) to efficiently maintain rank over millions of candidates. These patterns apply regardless of which technology implements them.
