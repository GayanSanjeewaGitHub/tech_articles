# Designing TikTok: System Design for a Read-Heavy Short-Video Platform

**Intuitive Takeaways (5 Key Points)**

- **The system is overwhelmingly read-heavy — design around that fact first:** The vast majority of traffic is users scrolling through feeds, not uploading. This single insight drives every major decision: read-only database replicas offload the primary, a Redis pre-cache stores curated video lists per user *before* they even open the app, and a CDN fronts blob storage so viral videos (one creator, ten million viewers) never hammer your origin servers. If you design uploads and reads symmetrically, the read path collapses under load.

- **Separate video bytes from video metadata — they live in fundamentally different storage systems:** The actual video file (compressed H.264, ~5 MB for a minute) goes to blob storage (S3). The metadata (video ID, creator ID, caption, blob URL) goes to a relational database. This split exists because blob stores are optimized for large immutable objects with built-in replication, while relational databases are optimized for structured queries and joins (e.g., "give me all videos from users I follow"). Mixing them would cripple both access patterns.

- **Pre-caching the feed is the key latency trick:** Instead of computing "which 10 videos should this user see?" at the moment they open the app — which means hitting the database, running the recommendation logic, and fetching blob URLs all under latency pressure — a background **pre-cache service** continuously builds and refreshes per-user playlists in Redis. When the app fires a GET request, the response is already assembled. This also defuses the thundering-herd problem: a million users opening the app simultaneously hit a cache, not a database.

- **Database sharding is the write-side scaling answer, and it needs its own routing layer:** When upload traffic 10x's, a single write database becomes the bottleneck. The solution is sharding — partitioning writes across multiple database instances (e.g., by region or user ID range). Critically, a **shard routing service** sits between the API and the databases so the application layer doesn't need to know which shard holds what. This is the same architectural lesson YouTube learned with Vitess: decouple shard awareness from business logic.

- **High availability comes from layered redundancy, not a single fix:** 99.999% uptime isn't achieved by one mechanism — it's the combination of a load balancer distributing traffic across multiple API instances (enabling zero-downtime deploys), read replicas absorbing query load, CDN absorbing video delivery, auto-scaling groups expanding under traffic spikes, and the pre-cache absorbing feed-read bursts. Each layer protects a different failure mode; remove any one and a specific category of spike or failure takes the system down.
