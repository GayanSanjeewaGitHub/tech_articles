# Agent Skills: Why Anthropic Stopped Building Agents and Started Building Skills

## 5 Intuitive Takeaways

- **"Code is all you need" — the agent underneath every domain turned out to be more universal than expected** — the initial assumption was that each domain (finance, research, DevOps) would need its own specialized agent with unique scaffolding and tools. In practice, a general-purpose coding agent (bash + file system) can pull data via APIs, analyze it with Python, organize it in the file system, and synthesize outputs in any format — all through code. The core agent loop is domain-agnostic; what changes per domain is the expertise layered on top, not the agent architecture.

- **Skills are just folders — and that simplicity is the entire point** — a skill is an organized collection of files (a `skill.md` with instructions, scripts as tools, assets, etc.) that packages procedural knowledge. No new runtime, no new protocol, no new abstraction. You can version them in Git, share them via zip, or drop them in Google Drive. Scripts inside skills replace traditional tool-call JSON formatting with self-documenting, modifiable code that lives in the file system until needed. This means anyone — including non-technical users in finance, legal, or recruiting — can create and share skills.

- **Skills are progressively disclosed to protect the context window — only metadata is loaded until the agent decides it needs a skill** — with hundreds or thousands of skills available, you can't stuff them all into context. At runtime, the agent sees only lightweight metadata indicating each skill exists. When it decides a task requires a specific skill, it reads in the full `skill.md` and accesses the folder contents. This is the same pattern as lazy loading in software: pay the context cost only when you actually need the capability, enabling composability at scale.

- **MCP provides connectivity to external systems; skills provide the expertise to use them well — they're complementary layers** — MCP servers give agents access to external tools and data (GitHub, Notion, databases). Skills orchestrate workflows across multiple MCP tools, stitching them together with domain-specific procedural knowledge. A Notion MCP server lets the agent read your workspace; a Notion skill teaches the agent how to do deep research across your workspace effectively. Connection without expertise is just API access; expertise without connection is just documentation. You need both.

- **Skills are a concrete step toward continuous agent learning — anything the agent writes down today can be used efficiently by a future version of itself** — when Claude saves a frequently-used Python styling script as a tool inside a skill, it's creating reusable procedural memory for its future self. As you work with the agent and provide feedback, it can update skills, acquire new capabilities, evolve them, and drop obsolete ones. This makes "agent memory" tangible and transferable: a new team member's Claude instance inherits the team's accumulated procedural knowledge from day one. The compounding value extends beyond teams into a community ecosystem, just like MCP servers.
