# Cursor's Vision: From Autocomplete to Self-Driving Codebases

## 5 Intuitive Takeaways

- **The evolution is autocomplete → synchronous agents → async cloud agents → self-driving codebases, and each transition is forced by a resource ceiling** — tab-complete hit its ceiling when models got good enough to generate whole features. Synchronous agents hit theirs because they eat local machine resources and you can't run tens of them simultaneously. Async agents need their own cloud VMs with full desktop environments to test work via computer-use, run resource-intensive test suites, and operate for hours (one refactor took 8 hours and made rendering 25x faster by migrating React to Rust). Each era begins where the previous one's resource model breaks.

- **The real bottleneck for async agents isn't code generation — it's reviewability** — when agents produce 3–4x more code than a human could locally, reviewing all those changes becomes intractable. The solution is "artifacts": agents produce videos of working features, research reports for ML experiments, and architecture diagrams — not just diffs. You review the output (a 30-second video of the feature working) instead of thousands of lines of code, and only dive into code once the demo matches your spec. The model's ability to produce useful, understandable artifacts ("model UX") becomes as important as its ability to write correct code.

- **Multi-agent with sub-agents solves the train-time/test-time mismatch that kills long-running single agents** — models are trained via RL on trajectories of hundreds of thousands of tokens. A single agent running for hours produces millions or tens of millions of tokens, far outside its training distribution, causing it to lose track and degrade. Sub-agents compress this: the outer planner runs for hundreds of thousands of tokens and fans out simpler subtasks, each well within training distribution. Different models specialize (OpenAI for planning/orchestration, Anthropic for UI, Gemini for computer-use/multimodal), creating a heterogeneous multi-model system.

- **"Self-driving codebase" means some changes merge with zero human review — and the codebase improves itself during off-peak hours** — the end state isn't just faster coding, it's agents that autonomously fix issues from the issue tracker when confidence is high enough, serve as primary on-call (humans become secondary escalation), and actively clean up tech debt and gnarly code with spare compute while engineers sleep. Already, agents monitoring training runs catch silent degradation and prevent crashes before anyone gets paged. Security review agents are finding vulnerabilities in PRs that would have shipped.

- **The role of the engineer shifts from "holding code details in your head" to "holding the entire codebase at a higher abstraction level"** — attention to detail still matters, but the details change: product taste, architectural decisions, deciding what to build. The browser experiment (a one-week, billions-of-tokens, tens-of-thousands-of-dollars run that produced a working but imperfect browser) shows that the bottleneck for building full products is now the quality of the spec and the ability to intervene at the right sub-points — not the ability to write code. Engineering becomes less about implementation and more about judgment, taste, and knowing where to look.
